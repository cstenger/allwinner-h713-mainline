# One startup path for cold and warm boots — plan, October 23

**Goal (release requirement):** after a warm reboot, HDMI input comes back
by itself, with live video on the panel and audible audio. A physical cold
cycle is not an acceptable recovery step.

**Approach:** stop giving warm boots their own branch. Every boot runs the
same proven sequence: U-Boot logo → MIPS launch → source 3 → 720p re-latch →
handoff, then the normal Linux receiver/audio/signal services. Like U-Boot
and Linux sharing the kernel DTS, there is one path to maintain and test.
Each boot establishes its own state instead of depending on what the last
boot left behind.

The Phase B teardown bench is **paused**, built but not run
([preparation](hdmi-evidence/2026-10-23-dsp-teardown-b-preparation/README.md)).
It localizes *where* the DSP patch is lost. A shared path doesn't need that
answer: it needs the DSP to be fresh after a warm reset, and it already is
(below). Resume the bench only if the warm test shows DSP state is the
blocker.

So there are two release blockers, and they are independent:

1. **HDMI does not start on warm boots.** This is the guard's choice, not a
   measured hardware limit. The shared path addresses it.
2. **The panel can go black after warm reboots.** This is a display problem
   that already affects today's warm boots. It needs its own fix, and the
   shared path must not hide it or be blamed for it.

## Target design

### U-Boot (`h713-hdmi.scr`, generated by `build-startup.py`)

* **One branch.** The cold sequence runs whenever MIPS status is 0 and the
  pre-launch census matches the cold-equivalent state (MIPS status/reset,
  GP7 zero, PPU bus, FIT/FDT sizes). There is no separate warm logo branch.
* **GP6 becomes a crash-loop guard, not a power-cycle latch.** Today it
  means "launched since power-on". New meaning:
  * `0` (cold) or `HDOK` (previous boot confirmed healthy) → write `HDMI`,
    then launch.
  * `HDMI` (a launch whose boot never confirmed health: wedge, panic or
    watchdog) → logo-only fallback, as the warm branch does today. One bad
    boot can never become a reboot loop.
  * Anything else → logo-only fallback.
* No changes to logo, launch, source 3, re-latch or handoff, which are all
  proven on cold boots.

### Linux

* **Driver path unchanged.** The receiver, audio (DSP `0/0` → patch → `1/1`
  gate) and signal owner start exactly as on cold boots. If a warm DSP ever
  reports anything but `0/0`, the existing gate refuses and capture fails
  closed. No new DSP access code.
* **Health ack.** After capture and signal are both active, one small unit
  writes `HDOK` into GP6 through the RTC nvmem (patch 0029). This is the only
  new software write to GP6. It replaces the "never clear GP6 in software"
  rule, which needs **your approval** before it ships.
* **Shutdown unchanged:** the orderly stop path and the hold guard as they
  are today.

### Explicitly out of scope

Changes to the DSP, teardown, MIPS park, domains or reset sequences, and
restarting firmware from Linux. Only if the warm test fails at a specific
step does the matching subsystem get an explicit reset, chosen from what
that step shows.

## First direct warm test (one cold cycle, one warm reboot, RAM-only)

**Built offline October 23:** [preparation and runbook](hdmi-evidence/2026-10-23-warm-shared-preparation/README.md).

Tests the real shared path with the real production modules. Nothing is
installed: the warm boot runs a RAM copy of the script, sent over YMODEM
at the U-Boot prompt, as the benches do. The installed script, GP6
semantics and saved environment stay unchanged.

**Preparation (offline, before asking for power):**
1. Generate `warm-shared.scr` from `build-startup.py`. It is the production
   cold sequence, gated on GP6 == `48444d49` (the value a cold-path boot
   leaves) instead of 0, and it does not rewrite GP6. It keeps every
   existing `itest` guard and adds the cold-equivalent census (MIPS status
   and reset words, GP7, PPU bus) before the logo. Unit tests: identical
   stages to the installed cold branch, apart from the GP6 condition.
2. `tools/serial/run-warm-shared.py`: catches the warm SPL, interrupts
   autoboot before `bootcmd`, so the installed warm logo never runs and MIPS
   stays at 0. It records the census, sends the script, runs `source` once
   and records UART. It refuses unless GP6 = `48444d49`, GP7 = 0, MIPS status
   = 0, and it sees exactly one warm SPL with no `pre_workspace` stage.
3. Host checker: services active, handoff present, DSP journal `0000/0000`
   → `1/1`, receiver state, capture RUNNING, xruns, and RMS of a 5 s
   `arecord` of the source's tone.

**Live sequence** (one operator "ready", with the source connected and
playing the standard tone clip):
1. Fully unplugged cold cycle → installed production cold boot → host
   checks a healthy HDMI session (`check-startup.sh`, capture, audio RMS).
2. `systemctl reboot` from the host. Verify an orderly service stop and a
   real reboot (UART shows a warm SPL, not the guard's poweroff).
3. The runner catches the warm prompt, then one `source` of `warm-shared.scr`.
4. Host checks the warm session exactly as in step 1.
5. **Operator:** after the lamp comes on, report the picture (live video /
   logo / black) and whether the tone is audible.
6. Checked poweroff. If the panel is black: unplug the cable at the
   projector, then reboot (known recovery).

**Result → next step:**

| Outcome | Meaning | Next |
| --- | --- | --- |
| Capture RUNNING, DSP `0/0→1/1`, audio RMS OK, picture live | Shared path works on warm | Repeat ×2, then production changes and a soak |
| Same, but panel black | HDMI recovery works; panel-black remains | Production changes plus the panel-black workstream |
| Fails at a `itest`/source-3/handoff stage | Warm firmware state differs at that stage | Diff that stage's registers against the cold capture; targeted reset of that block |
| DSP not `0/0` at driver start | Warm DSP not fresh on this path | Resume the bracket work, now for one specific question |
| Hang/wedge | Unknown state survives warm reset | Power cycle; compare UART to cold; nothing installed |

## What keeps it safe

* **Nothing installed.** The RAM script and the production FIT, modules and
  services are unchanged. Worst case is one power cycle; no boot loop is
  possible, because the next autoboot runs the installed warm branch.
* **One launch per warm boot.** The runner never retries `source`, and an
  uncertain stage ends the run.
* **Guards are kept, not bypassed.** Every stage `itest` from the proven
  cold script, the cold-equivalent census before the logo, the driver's
  `0/0` gate, the receiver owner checks, FIT/FDT size pins, and the hold
  guard on shutdown.
* **Known hard-lock windows are never touched:** CPUS/ARISC `0x07091xxx`,
  `0x06940000`, GP7. No DSP or lock access beyond the production driver's.
* **Lamp/fan (PB5):** held low only across the bring-up, as on cold boots.
* **Panel black is expected in some runs** and has a known recovery; it is
  recorded as its own observation and never counted as an HDMI failure.
* **Production adoption** comes only after repeat passes, with the GP6
  crash-loop guard and the health ack, each unit-tested, plus your approval
  of the new GP6 rule.

## Slimming the warm path (after the full sequence passes)

The aim is less duplication, not identical boots. Warm boots may skip a step
that turns out not to matter, so long as nothing breaks. The rule:

* **The first test runs the full cold sequence.** It is the control: if a
  slimmed variant failed first, we couldn't tell whether warm boots or the
  removed step were at fault.
* **Remove one step at a time.** Each variant must pass the same
  acceptance check, `check-warm-shared.py` (DSP `0/0`→`1/1`, capture
  RUNNING, tone level, picture), on at least two warm reboots.
* **Iterating gets cheap.** A warm-shared boot leaves GP6 at `48444d49`,
  so warm→warm repeats need no cold cycle. The runner gains a warm-only
  mode for this.
* **Abrupt resets count.** A watchdog or panic reset skips Linux's orderly
  teardown, so a step may only be skipped if the variant also passes after a
  SysRq-b reset, or if the skip is limited to resets known to be orderly.

Candidates, as the cold UART shows them:

| Step | Warm candidate? | Why / how to decide |
| --- | --- | --- |
| Two firmware starts: logo (workspace clear, release, quiesce), then a second workspace clear and the source-3 launch | **Yes, and maybe for cold too** | The logo start exists to draw the logo before the long-lived launch. Test one launch that draws the logo and goes on to source 3. This is the largest duplication in the path. |
| Panel: 3 s supply-off wait + 550 ms pre-delay | **Not yet** | This is panel power sequencing, and panel-black is a panel/rail-state problem. Leave it until that is understood. |
| Reloading firmware/logo assets from FAT | Maybe | DRAM survives a warm reset, but U-Boot and Linux may have overwritten it. Only skip on a verified CRC of the retained copy. The saving is small. |
| FIT/FDT size checks, FDT fixups | No | Cheap, and they guard the production image. |
| MIPS launch + source 3 | No | MIPS is parked by the reset; there's no receiver without it. |
| DSP patch (Linux) | No | Measured `0/0` after a warm reset, so it must be reloaded. |
| 720p re-latch | No | The firmware rewrites the timing on every source-3 launch. |
| Handoff property | No | It's how Linux knows the receiver is live. |

## End goal: slim everything and minimize boot time

Once warm recovery works, cold and warm boots both get the same treatment:
remove every step that isn't needed, and make boot time a tracked number.

* **Measure first.** Each run's UART and `events.log` give a baseline per
  stage: SPL → U-Boot prompt → script → logo → MIPS launch → source 3 →
  re-latch → kernel → services ready → capture RUNNING. U-Boot lines carry no
  timestamps, so the runner should stamp stage markers on the host as they
  arrive. That makes every later change a measured before/after.
* **Then cut, one change at a time,** with the same acceptance check as warm
  slimming (`check-warm-shared.py` plus the picture), on cold and warm boots,
  including an abrupt reset. Known candidates:
  * the double firmware start (logo, then relaunch);
  * the 3 s + 550 ms panel waits, once panel-black is understood;
  * the 5 s autoboot delay, kept only as long as recovery needs it;
  * reading the 7.8 MB FIT from FAT (~0.5 s);
  * the ~20 s from kernel start to HDMI services ready (unit ordering,
    `After=user@1000`, module load, DSP patch upload).
* **Don't remove safety.** Cheap guards (itests, size/CRC pins, the DSP
  `0/0` gate, the hold guard) stay unless replaced by something equivalent.
  Time comes out of waits and duplicated work, not checks.
