# Handoff — 2026-08-30

Session goal was to follow up the CPU_COMM lead reopened on 2026-08-29. Two
leads are now closed, one is scoped-but-blocked, and one real defect was found
in our own code. Most of it cost no bench time: the disassembler did the work
that three sessions of register permutation could not.

Branch `h713-display-video-path`. Commits `10d9087`, `6a0a796`, `47493b4`.

## The headline: the 1080p window was a red herring, settled statically

`THal_Vp_Wce_GetWindow` reporting 1920x1080 on a 720p panel looked like a strong
lead on 2026-08-29 and was recorded with an explicit caveat that it had not been
shown to be causal. That caveat resolved the benign way, and entirely by
disassembly.

The three `Wce_*` routines are not peers:

| routine | what it does |
| --- | --- |
| `Wce_GetWindow` `0x8b14cef0` | copies three firmware **globals** to the caller. No hardware. |
| `Wce_SetWindow` `0x8b14cd18` | stores into those same globals, then calls `0x8b1099c8` |
| `Wce_GetActiveWindow` `0x8b14cf64` | **virtual call** through a live object's vtable -- a genuine query |

`0x8b1099c8` is a stub: `jr $ra; addiu $v0, $zero, 1`. It is the only thing
`SetWindow` calls that is not a trace or a `memcpy`. **`SetWindow` therefore
cannot change what is on the panel**, and `GetWindow` only ever reads back what
`SetWindow` wrote.

Nothing ever wrote them. `0x8b22f1b0` in the **static image** already reads
`00000000 00007800 00000000 00004380`, byte-identical to the live board. The
1920x1080 is also a literal inside `SetWindow`'s own prologue -- the default it
substitutes for null arguments.

So `GetActiveWindow`'s 1280x720 was the live answer all along. **Do not spend
bench time calling `SetWindow`.**

## The suppression routines: tested, negative, but the test was not valid

The other half of the 2026-08-29 reopening was six suppression routines
(`EnableBlackScreen` and friends), justified on 2026-08-30 by tracing them to a
real mechanism -- a 12-byte opcode message posted to a ThreadX queue serviced by
an `app_bottom` worker thread, through a lazily-constructed singleton at
`0x8b253570` whose initialiser is called unconditionally from `0x8b15340c`
(our marker 55). That chain is sound and is confirmed by name at every hop
(`OnHalMiscDisableBlackScreen`, `./hal_func.cpp`).

Hardware result, at the U-Boot prompt under `init 0x34`, MIPS alive, live row
`chan=0 pid=8b8f275c`:

| call | transport | panel |
| --- | --- | --- |
| `2f02f7dd` no-op (control) | reply 1 ms | -- |
| `a30d4c6b` `EnableBlackScreen` | reply 0 ms | **no change** |
| `b66041d8` `DisableBlackScreen` | reply 0 ms | no change |
| `2fdcdc6f` `EnableVideoFreeze` | reply 0 ms | no change |
| `0152f134` `EnableScreenCover` | **no reply** | no change |

Register evidence, which does not depend on anyone watching: dumps taken with
black screen enabled and again after disabling are **identical across all 22
blocks** `h713_disp dump` covers, except the free-running LVDS scan counter.
Baseline saved as `docs/reference/uboot-init34-mips-alive-idle-2026-08-30.txt`.

**The observable was wrong, and this is the important part.** The logo renders
on the **OSD** channel `0x05600140`. These are `THal_Vp_*` -- *video processor*
-- routines, which act on the **video** channel `0x05600100`, empty in this
state. The test cannot discriminate "inert" from "working correctly, aimed at a
layer with nothing in it". The static side says the second is entirely possible:
`0x8b1177ac` performs a registered-handler lookup keyed on a field of its
argument, and with no video window registered it would legitimately do nothing.

So this lead is **scoped, not closed**. Calling it dead would overread a test
that could not have detected success.

## A second 1920x1080, in our own code, and NOT the same thing

`tools/video/decd-client.c` `fill_video_info()` declared `W 1280` / `H 720`,
derived the source dimensions and output window from them, then hardcoded
`0x7800`/`0x4380` into the crop and display-frame structs -- under a comment
reading `identity setDisplayFrame()`, which it was not.

Keep the two apart:

- the firmware globals behind `Wce_GetWindow` are **inert** -- no path to any register
- this struct is handed to the firmware **on every frame submit** -- live input

That they share the encoding is measured, not assumed. The
`{x, width, y, height}` 1/16-pixel layout came out of the firmware disassembly
and was validated against the panel; `W << 4` / `H << 4` give `0x5000`/`0x2d00`,
exactly what `Wce_GetActiveWindow` returns. `0x7800`/`0x4380` is also the
firmware's own linked-in default, the likely origin of the copy.

Changed to derive from `W`/`H`. **UNTESTED ON HARDWARE.** No stock VideoInfo
capture exists to confirm the vendor sends source-sized values here rather than
always sending 1080p and letting the pipeline scale. Reverting is four lines.

## Free explanation of the fmt 4 photograph

`fmt_attr_tbl` in patch 0013 explains the 2026-08-28 stock photograph without
any new work. Format **0** is `{2,2,2,2}` -- 8-bit 4:2:0, NV12. Format **4** is
`{1,1,1,1}`, no chroma subsampling. An NV12 buffer read as fmt 4 consumes two
source lines per output line: the 2x-repeated, half-height, colour-shifted
image that was photographed.

The client asks for format **6** and the firmware programs **4**, so the
translation is firmware-side and the VideoInfo `+0x40` mapping (currently `11`)
is still unknown. That mapping is the remaining piece of the fmt work.

## Corrections to things believed earlier

- **"CPU_COMM has ten live routines nobody has called"** (mine, 2026-08-30
  morning) was measured at the **adapter** level -- real prologue vs
  `jr ra; nop`. `Wce_SetWindow` passes that test and is inert. Adapter-level
  liveness proves nothing; check what the implementation actually *reaches*.
- **`0x8b12bb30` is not a fixed-point converter**, it is a plain 16-byte copy.
  The 1/16 reading rests solely on the 1280x720 match.
- **`Wce_GetWindow` fills two structs and a scalar**, not one. Only `p1` was
  read on hardware; the static image supplies the rest (`p2` also 1920x1080,
  scalar `2`). No re-run needed.
- The **first cross-reference scan** for writes to `0x8b253570` reported **zero
  stores**, which would have supported a confident and wrong "nothing ever
  registers it". It only tracked `lui`-formed bases and missed
  `sw $s1, 0x3570($s0)` at `0x8b106bc0`. **When a scan answers "none", check
  that it could have seen one.**

## Operational hazards, each of which cost time here

- **Never call `0152f134` (`THal_Vp_EnableScreenCover`).** It wedges CPU_COMM:
  afterwards the same no-op that had round-tripped in 1 ms is never accepted.
  U-Boot's `reset` then printed `resetting ...` and produced no further output
  at all. **The board needed a physical power cycle.**
- `h713_disp init <id>` prints `Power-cycle before another init`. Believe it.
- `reboot-to-uboot.py` types `reboot`, which is the *Linux* command. At the
  U-Boot prompt that is an unknown command and nothing resets. A `reset`
  variant is in the scratchpad; fold it in if this recurs.
- Piping a background `console.py` through `tail` buffers everything until the
  command exits, so interim output is invisible. Redirect to a file instead.

## Tools added

`tools/mips/disasm.py` -- capstone-based MIPS32LE disassembler for the display
firmware, with `--self-test`.

It exists to centralise **one fact that has already gone wrong once**: the
firmware base is `0x8b100000`. A previous helper carried `0x8b101000`, 4 KiB
high, and consequently described unrelated code as the CPU_COMM adapter, which
is how the bogus zero-argument `THal_Vp_Init` ABI came to be believed.
`--self-test` asserts the base against routines known to be stubs and known to
be real, so a wrong base fails loudly instead of producing confident nonsense.

Useful invariants it encodes:

- file offset = `VA - 0x8b100000`
- MIPS VA `0x8b1xxxxx` = **ARM physical `0x4b1xxxxx`** (subtract `0x40000000`)
- `lui`/`addiu` pairs are folded into the address they compute, and register
  tracking is **retired** on writes and across calls -- an earlier version kept
  crediting stale values and printed wrong addresses

**This is now the blocker.** Settling the suppression lead needs the calls made

### START HERE: a Linux port already exists and is disabled

**Do not write this from scratch.**
`patches/kernel/0014-soc-sunxi-add-cpu-comm-ipc.patch` is an **8440-line**
CPU_COMM/IPC driver. It **is** in `patches/kernel/series` (line 13), so its
source is applied to the tree -- it is simply never built:

```
patches/kernel/board/hy200_qz713df_a1_defconfig:214:
    # CONFIG_HY310_CPU_COMM is not set
```

Config symbol `HY310_CPU_COMM`, module `hy310-cpu-comm`, at
`drivers/soc/sunxi/cpu_comm/`. Consistent with the live board, where
`0x03003000` is unclaimed in `/proc/iomem`.

So the task is **enable it and correct it against U-Boot's verified transport**,
not greenfield work.

**One defect is already located.** At patch line ~4109 the driver packs the
doorbell as:

```
raw[31:16] = msg_type (0..3)
raw[15:0]  = direction/intr_type (stock: 2)
```

U-Boot's notes, written from the firmware's own dispatcher at `0x8b122678` and
confirmed on hardware, say this is wrong: *"The doorbell word is the message
type and nothing else... There is no `msg_type<<16` field and no `intr_type`
field; the Linux tree's packing is not what this firmware expects."* **A CALL is
doorbell `0x00000000`.**

**A second area to check** is the register model. The driver assumes
`ARM = User 0 @ 0x03003000`, `MIPS @ 0x03003400`. The addresses actually
verified live are the ones in the table below -- TX doorbell `0x03003874`, RX at
`0x03003164`/`0x03003174` -- derived from the firmware's own msgbox send at
`0x8b12199c` forming `base + (chan << 2) + (field << 10) + (user << 8)`.
Reconcile the two before trusting any of it.

Treat the rest of the driver with the same suspicion: it predates every
hardware-verified fact below, and the `THal_Vp_Init` zero-argument ABI in that
era was also wrong.

### Transport

| what | address | note |
| --- | --- | --- |
| doorbell (TX) | `0x03003874` | single write; **the word is the message type and nothing else** |
| TX count | `0x03003864` | |
| version | `0x03003810` | reads `0x00020000` on a live msgbox |
| TX IRQ enable | `0x03003830` | |
| RX count | `0x03003164` | MIPS -> ARM |
| RX data | `0x03003174` | MIPS -> ARM |
| msgbox BGR | `0x0200171c` | bit 0 gate, bit 16 reset |

- **A CALL is doorbell `0x00000000`.** Types: `0` CALL, `1` RETURN, `2`
  CALL_ACK, `3` RETURN_ACK. There is no `msg_type<<16` and no `intr_type`
  field -- the Linux tree's packing is *not* what this firmware expects.
- H713's msgbox is **edge-triggered** (H6's is level-triggered), so U-Boot
  pulses `BIT(3)` on `0x03003830` and then writes `0`.
- An unclocked msgbox **swallows the doorbell silently**. U-Boot sets bits 0 and
  16 of `0x0200171c`.

### Memory, and why /dev/mem will work

Both shared regions are `no-map` reserved, so `CONFIG_STRICT_DEVMEM` does not
block them -- the same reason `mem-fill` worked on `0x6c100000` and could not
touch CMA:

```
mips_reserved:     mips-firmware@4b100000   reg = <0x4b100000 0x0e41000>  no-map
cpu_comm_reserved: cpu-comm@4e300000        reg = <0x4e300000 0x00500000> no-map
```

The channel table at MIPS `0x8b2544b8` = ARM `0x4b2544b8` is comfortably inside
the first. The CPU_COMM slot ring observed live (`base=4e302778`, `slot 4 @
0x4e3029c0`) is inside the second.

**Verified on the live board 2026-08-30:**

- `0x03003000` is **not claimed** in `/proc/iomem` -- no conflict
- `sun6i-msgbox` is registered as a driver but has **no bound device** (only
  `bind`/`uevent`/`unbind`), so nothing else owns the mailbox
- `clk_ignore_unused` is on the kernel command line, so a bus clock U-Boot
  enabled is not turned back off

### The argument ABI (already cracked, do not re-derive)

- Parameters: a leading dummy, then up to three pointers read at `+4`/`+8`/`+12`
- **Pass ARM physical addresses unmodified.** The `0xa0000000` OR inside the
  adapter is its own business; subtracting `0x40000000` is wrong and was the
  error that made the first attempt fail
- Adapters map with `ext rX, rX, 0, 0x1c` then `or 0xa0000000`, and `movz`
  preserves a null
- Output is `{x, width, y, height}` in **1/16-pixel fixed point**
- The destination must be **untouched workspace**. Planting sentinels first
  creates dirty ARM cache lines and the read comes back stale

### The hazard

MIPS alive + Linux + DECD submitting **hard-locks the SoC in seconds to tens of
seconds** (this is why `mmio-poke` phase 3 is fire-and-forget: no hold, no
restore). Design the Linux caller the same way -- configure, fire, exit, and get
the observation from the panel rather than from a leisurely readback.

The 2026-08-30 suppression test established that Linux boots cleanly with
`preboot` set to `h713_disp init 0x34` instead of `auto 0x34 logo`, with the
MIPS still alive. Keep bounded DECD tests short despite that successful run;
earlier MIPS-plus-DECD experiments have still locked unpredictably.

# Continuation — 2026-08-30, later

Everything above was written before CPU_COMM was built. Four things happened
since: the driver was enabled and made to probe on hardware, the firmware's
display code became statically analysable for the first time, the format
question was answered and confirmed on the bench, and one of my own findings

## CPU_COMM: enabled, corrected, probing

Patch 0014 was an 8440-line driver sitting in the series and never compiled.
It is now `=m` with the DT node enabled, and **it probes**: clean bind, both
chardevs, 1224-slot routine table, SMM heap, 18/18 VP routes, no WARN or BUG.
Evidence in [`reference/cpu-comm-linux-probe-2026-08-30.txt`](reference/cpu-comm-linux-probe-2026-08-30.txt).

Three defects were fixed to get there.

**The msgbox register model was wrong in both directions.** It assumed
0x400-byte per-user regions; the verified addresses are TX doorbell
`0x03003874` (count `0x864`) and RX `0x03003164`/`0x03003174`. The doorbell
also sat *outside* the ioremap — the block was mapped 0x800 long and the
doorbell is at `+0x874`, so every send wrote past the end.

**The doorbell packing.** The handoff above says the driver packs
`raw[31:16]=msg_type`. That is what the *comment* said; the TX line already
sent a bare type. The wrong packing was live on the **RX** side and
mis-dispatched everything: `0x00000002` (CALL_ACK) decoded as type 0 = CALL,
and `0x00000000` (CALL) as direction 0 = ARM rather than MIPS.

**The 32-bit shared-pointer model.** The u32 width is fixed by the protocol —
the MIPS reads these structures — but `(u32)&x` recovered with
`p | 0xffff800000000000` is garbage on arm64. Replaced with `cc_ref`: bit 31
clear means an ARM-physical address in the shared region, bit 31 set means a
tagged driver-private arena. Chasing it turned up non-terminating list loops,
a 4-byte slot read as `*(u32 **)`, and two 8-into-4-byte stack writes. The
shared half is confirmed on hardware against ring addresses U-Boot recorded
independently (`fifo base 0x4E302778`, `slot 4 -> 0x4E3029C0`).

Also fixed: `InitCommMem` wiped the shared region unconditionally, directly
under a comment describing the conditional it needed. Harmless with the MIPS
parked; with the firmware running — the only case where this driver is useful
— it would destroy the live queues. It now adopts a region that is valid *and*
has the MIPS out of reset, with `force_init` to override.

**Still unexercised: no message has been exchanged.** The corrected doorbell,
the TX_IRQ_EN pulse and the tagged-local half of the encoding have never run.
That is the next milestone, and it needs the MIPS alive.

**A pre-existing defect this turned up:** the probe logs `wrote ShMemAddr` but
`0x03061024`/`0x03061028` read back zero. The write does not stick with the
MIPS in reset, so the coprocessor never learns the shared-memory base that way.

## The firmware's display code is now readable

Every previous search of `display.bin` for display registers found nothing,
in any encoding. The reason is an offset:

    MIPS address = ARM physical + 0xB5000000

so AFBD is at `0xba600000`, the LVDS PHY at `0xba1c0000`. Search for `0xba6…`,
never `0x056…`. With that, the firmware is visibly writing `0x05600010` at 11
sites, which turns the 08-28 *inference* that it programs the video source into
something you can read.

## The format question is answered

The resolver at `0x8b1a31e8` is a bounds-checked jump table through 16 entries
at `0x8b2078a4`. Full table in
[`reference/firmware-format-mapping-2026-08-30.md`](reference/firmware-format-mapping-2026-08-30.md).
Confirmed on the bench, control first:

    input 11  ->  0x05600010 = 0x03000413   fmt 4   table said 4
    input  0  ->  0x05600010 = 0x03000013   fmt 0   table said 0

`0x03000013` is stock's value. The client now sends 0; `DECD_FMT` overrides it
for sweeping. This also closes the caveat that VideoInfo `+0x40` was only
*correlated* with the resolver's input — it is the input.

**fmt is necessary, not sufficient.** Forcing fmt 4 onto stock gave a broken but
visible picture, not black. This removes a known-wrong input; it does not put
video on the panel.
