## The plane question: answered, negative

Goal was hardware YUV→RGB with neither CPU nor GPU, which needs a video plane.
Seven attempts, all negative, detailed in
[`ge2d-plane-open-re.md`](ge2d-plane-open-re.md). The decisive one flashed a
modified U-Boot injecting 26 mirror writes into the bring-up sequence itself
(only U-Boot proper at LBA `0x49ac00`; first stage untouched; backed up and
restored byte-identical afterwards).

The diagnostic fact:

```
0x05600144   plane 1 READY latch   reads 0   consumed every vsync
0x05600104   plane 0 READY latch   reads 1   written, never consumed
```

Channel 0 is not serviced. Configuration survived into live scanout for the
first time and it was still ignored; operator confirmed no logo, console only.

### …and then the framing turned out to be wrong (late in the session)

The operator mentioned the panel is LVDS, which sent me to `panel_config.ini` —
shipped beside the MIPS firmware, never opened in this entire investigation:

```
PanelDualPort        = 0     <-- single-port LVDS
OddEven              = 0
PanelODDDataCurrent  = 7     <-- odd/even lane drive strengths exist
PanelEvenDataCurrent = 7
```

The peer project's parser independently decodes `0x05600140` as carrying a
**`dual_port` bit**.

**Hypothesis: AFBD "channel 0" and "channel 1" are the odd and even LVDS ports,
not two compositing layers.** On a single-port panel channel 0 is unused
*hardware*.

Corroborated two ways:

- **Hardware, independent of this project:** the operator has driven this same
  panel from a Geekworm HDMI-to-LVDS board configured as **1-port LVDS**, and it
  worked.
- **The file makes a prediction that holds:** if channels map to ports, no
  shipped variant should differ in port config. All 8 DE variants carry
  identical `ctrl = 0x03001901` and `global = 0x80000020`, across 640x360 to
  1920x1080. Only geometry varies.

Still inference: that channel 0 *is* the second port. A fused-off block looks
identical and we have no datasheet. **It does not matter which** — both readings
say channel 0 is unusable, so:

> **The question was never "how do we open a second plane". It is "how do we
> make the one channel fetch YUV."** The two-plane framing shaped this whole
> session and was wrong from the start. Do not restart the plane work.

This is the fourth time an assumption baked into the register map turned out to
be the blocker. Concrete lesson: **read the vendor's configuration files before
reasoning from register layout.** `panel_config.ini` would have reframed this on
day one.

## External review — corrections to my work

A reviewer with Allwinner display knowledge went over the brief. Several points
are corrections, not suggestions. Verified where checkable:

1. **`tgd_init_planesetting` is not an ioctl entry.** My caller analysis matched
   only resolved `bl` targets and ignored `R_ARM_CALL` relocations, so
   "no intra-module callers" meant "none I looked for". Re-checked:
   `tgd_init_planesetting <- init_svp @0x99ac` (probe-time) and
   **`tgd_put_plane_info <- svp_ioctl @0x8ffc`** — the latter is the real
   runtime path. Module exports only `AllocateFB`, `FreeFB`,
   `InitFBManagement`. **Recovering that ioctl's command and payload is now the
   best vendor-driver experiment.**
2. **Attempt 7 did not control placement as claimed.** READY was asserted
   *before* clocks/INCAP/LVDS and the MIPS release. It should be asserted only
   after clocks run, LVDS is finalised, and at least one vblank has passed.
   Configure early, latch late. **This is a re-test, not a dead end.**
3. **"Fully and correctly configured" is overstated.** The 26 writes cover AFBD
   and OSD only. The window pair (`0x05280040/80`), VBlender-ish
   (`0x0520002c/34`), DE2 companion (`0x05288000`/`0x0529c000`), both LVDS pairs
   and the three skipped runtime LVDS RMWs are all untried plane-specific state.
4. **Scope the LogoRegData claim** to "no *boot-time* configuration opens two
   planes". Android runtime ioctls, CPU_COMM and firmware actions are unmeasured.
5. **A second simultaneous plane may not be required.** Full-screen video could
   *replace* the RGB plane. The requirement is a **serviced YUV fetch route**,
   not necessarily two planes.

## Highest-value next step: a small mpv patch

This is the review's most useful finding and it sidesteps the plane problem
entirely for the common case.

`--hwdec=vaapi` fails **before decoding**: mpv's DRM/EGL context looks for a
render node on the panel's KMS device, finds none (our AFBD card has no render
node), records `render_fd = -1`, and the VA-API backend then refuses to create a
display. Hence the fallback to `vaapi-copy` and its ~44 MB/s uncached CPU read.

Everything downstream already works: our VA driver advertises `DRM_PRIME_2`,
`RequestExportSurfaceHandle()` exports capture buffers as NV12 DMA-BUF, and mpv
already imports composed two-plane NV12 as R8/GR88 EGL textures.

The experiment is roughly:

```c
int fd = params->render_fd >= 0 ? params->render_fd : params->fd;
return fd >= 0 ? vaGetDisplayDRM(fd) : NULL;
```

Our `v4l2_request` driver ignores that DRM fd anyway — it opens `/dev/video0`
and `/dev/media0` itself — so the panel's primary KMS fd should be enough to
bootstrap libva with `LIBVA_DRIVER_NAME=v4l2_request`.

Acceptance: mpv reports `Using hardware decoding (vaapi)`;
`vaExportSurfaceHandle()` succeeds; no CPU read of capture buffers; VE, panfrost
and AFBD IRQs all advance; seeking, repeat playback, H.264, HEVC Main and Main10
all survive.

**Do not add a fake render node to the panel driver.** Render nodes are for
genuine render-client UAPI; that is an architectural shortcut, not a fix.
Weston/Wayland is a stock-mpv fallback (mpv can build a VA display from
`wl_display`), but try the small patch first.

Note this still uses panfrost for YUV→RGB — it is the *zero-copy* target, not
the *no-GPU* target. Those are two different goals and only the first is close.

## Reordered investigation plan (reviewer's, better than mine)

1. **Boot stock Android and snapshot registers during actual full-screen
   hardware-decoded playback**, not just idle — the vendor may create the video
   plane only while playing. Record both channels, READY, mixer, VBlender, DECD,
   IRQs, buffer addresses. *Most decisive single experiment available.*
2. Recover and invoke the `svp_ioctl` command reaching `tgd_put_plane_info`;
   trace `io_accessor_write_reg`.
3. Compare register state across U-Boot phases: after LogoRegData, after clocks,
   either side of the MIPS release, after LVDS finalise, after first vblank.
4. Retry the injection with **READY deferred to the live phase** (point 2 above).
5. Trace CPU_COMM while Android starts/stops video.
6. Investigate DECD's raw/bypass path, single kernel owner for its shared
   registers/reset/IRQ. Cedrus emits NV12/tiled, never AFBC, so DECD's
   compressed path is not directly usable.
7. Only then disassemble `display.bin`.

## Productization gaps

- **The rootfs does not ship the VA driver.** `tools/video/build-va-driver.sh`
  says outright that a fresh flash loses hardware decode;
  `tools/rootfs/build.sh` installs build deps but not the resulting `.so`.
  Package a board-ABI-matched `.deb` or add an image-build stage.
- **Card numbering** is inconsistent across older docs. Reuse the runtime
  discovery already in `soak-display-only.sh`; never encode `card0`/`card1` in a
  product command.
- **The uncommitted resolution-change patch** carries a comment claiming FFmpeg
  recreates its context at new geometry — the trace proves otherwise. Latent
  cleanup, keep out of the shipping series.
- **Main10 is an 8-bit approximation** from the primary plane, not native 10-bit.
- **Mid-stream SPS resolution change** remains a known mpv/FFmpeg VA failure;
  keep it in the acceptance matrix.

## Two method lessons worth carrying

**Check the artifact, not the source.** Removing a patch from the series
reverted the build digest to a tree I had hand-edited, so `build.sh` reused a
"matching" cache entry that still contained the change. Caught only by grepping
the built tree.

**Relocations are calls too.** The `tgd_init_planesetting` error above came from
searching disassembly text for `bl` targets in a relocatable object. Any caller
analysis on a `.ko` must read `R_ARM_CALL` relocations as well, or it silently
under-reports.
