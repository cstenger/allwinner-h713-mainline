## 1. The display corruption was never in the video stack

**It was the CPU's 1416 MHz operating point.** Patch 0055 removes it; the
ceiling is now 1296 MHz.

| ceiling | transitions | result |
| --- | --- | --- |
| 1416 | yes | **crash in 40–90 s** (n=3) |
| 1200 | yes | clean, 20 min |
| 1296 | yes | clean, 20 min |
| 1296 (built kernel) | yes | **clean, 45 min / 2707 s** |

Validated on the built kernel over serial: `deaths=0`, `gpu_delta=1,316,959`,
`afbd_delta=161,473`, zero crash patterns, board up 52 minutes without a
reboot. That is 3.2x the longest crash latency ever recorded (848 s).

**Frequency transitions are innocent** — the capped arms ran `schedutil` with
`khz` visibly moving. Only the top point matters.

**The vendor never uses 1416.** Its `allwinner,sun50i-operating-points` driver
(disassembled from the stock 32-bit ARM kernel, probe at `0xc074f808`) reads the
`speed` nvmem cell, assembles it little-endian with no shift or mask, and
formats it `"0x%8.8x"` as the OPP prop name. That cell is `vf-table@00`,
`reg = <0x00 0x02>` — **two bytes** — while every key in the stock CPU table
exceeds `0xFFFF`, so none can ever match, every die falls back to plain
`opp-microvolt`, and there 1416 reads `<0x00>`: no voltage.

**Why it hid.** It presented as a video bug, so it was chased through cedrus,
VA-API, the IOMMU, panfrost's dma-buf import and CMA — each excluded by
experiment. Two crash traces landed *inside* the DVFS path and were dismissed as
"a hot path". `ffff` → `faef` in a corrupted pointer is `XOR 0x0510`: three
flipped bits, not an overwrite.

**Why it was not caught at bring-up:** 1416 was qualified with a **2-minute
CPU-only load at 68 °C**. The workload that breaks it is tens of minutes of
GPU + display at 78 °C. The DMM voltages were right; the frequency point was
never in the vendor's table.

**Superseded claims** (corrected in place in `docs/vaapi-scope.md`): "the
discriminating variable is where the scanout buffer lives" — refuted by patch
0054; the 2x2 that replaced it — its CMA half dies to the same experiment; run D
as evidence that a carveout protects anything — demoted.

**Cost:** CPU ceiling 1416 → 1296, about 8%. **1392 MHz @ 1100 mV is the
vendor's top usable point** and would recover most of it, but it is **untested
here** and deliberately not added — shipping an unvalidated top OPP is exactly
what caused this.

## 2. HEVC decodes bit-exact through stock ffmpeg

```
h01-640x480-main    PASS (va) bit-exact, ve+25
h02-1280x720-main   PASS (va) bit-exact, ve+25
h03-640x480-nowpp   PASS (va) bit-exact, ve+25    H1: 6 pass, 0 fail
H.264 (unregressed)                               VA1: 5 pass, 0 fail
```

`src/h265.c` is **bootlin PR #44** (head `c488d8df`) verbatim, lifted onto our
PR #38 base. **Neither upstream PR works alone on this hardware:** #38 has the
format-ordering cedrus requires, #44 has the modern HEVC port. #44 on its own
cannot decode H.264 *or* HEVC here — CAPTURE clamps to 16x16, then `EBUSY` on
the OUTPUT format, which is the V4L2 stateless spec's mandated order enforced by
`cedrus_s_fmt_vid_out()`.

**The last bug was an uninitialised variable.** `context->h264_start_code`
decides whether an Annex-B start code is prepended, and it is assigned
**nowhere** — `h264_get_controls()` is defined and never called. H.264 had been
decoding bit-exact because the heap happened to hold zero. cedrus accepts only
`START_CODE_NONE` for **both** codecs.

Also fixed: `nal_unit_type` was read from that start code (0 = `TRAIL_N`,
non-reference, passed straight to hardware); and the coded pixelformat was
hardcoded to `H264_SLICE`, so HEVC selected cedrus's H.264 codec ops and
produced an all-zero frame.

### Method note worth keeping

Three hypotheses were refuted from userspace first — an off-by-one in
`data_byte_offset` (`+1` and `+3` both tested), missing entry-point offsets, and
"x265 changed something else with `wpp=0`". Each was cheap; none was right.
What ended it was **patch 0056**, dumping the controls cedrus receives so the
same stream could be run through GStreamer and the shim and diffed. That
produced three real bugs in one pass. **Reach for the oracle's own values
sooner.**

### Known limitations, stated not hidden

- ~~**Scaling lists are not passed.**~~ **CLOSED later the same day** by
  `patches/libva-v4l2-request/0005`, with two new vectors (`h04`, implicit
  default lists; `h05`, explicit custom lists with DC coefficients) that the
  old gate was structurally blind to — every earlier vector has
  `scaling_list_enabled = 0`, and cedrus gates the write on that SPS flag, so a
  driver filling nothing scored bit-exact on all of them. Both showed
  `MISMATCH (va) ve+25` before and bit-exact after; the oracle was bit-exact
  throughout, so cedrus was never at fault. H1 is now 10 pass / 0 fail with
  H.264 unregressed at 5/5.
- **Entry point offsets are not passed** and are not needed — ffmpeg reports
  `num_entry_point_offsets = 0` even for WPP streams. This **corrects an earlier
  claim in this repo** that h01/h02 required them.
- Two PPS flag bits are wrong (`DEBLOCKING_FILTER_CONTROL_PRESENT`,
  `UNIFORM_SPACING`); neither is referenced in cedrus, so both are inert here.
- `h264_start_code = false` is right for cedrus, wrong in general. Querying the
  per-codec `START_CODE` control is the correct form.

**Two traps that cost real time:**

1. ~~**A cedrus `frame processing timed out!` wedges the VE for every
   client**~~ — **REFUTED 2026-08-23.** The engine recovers from ten
   consecutive timeouts, for the shim and for GStreamer alike. The real wedge
   is **three or more concurrent decoders**, which deadlock inside
   `v4l2_m2m_cancel_job()` and survive SIGKILL; a failing run that left
   processes behind would produce exactly the symptom this rule was written
   from. Two concurrent clients are safe. See
   [`docs/decode-production-readiness.md`](decode-production-readiness.md).
2. **`/tmp` on the board is tmpfs** — scripts scp'd there vanish across reboots.
