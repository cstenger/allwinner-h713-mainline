# The scaler test card — how to read it

Generated by [`tools/display/make-scaler-testcard.py`](../../tools/display/make-scaler-testcard.py).
Vector source, rasterised natively per resolution.

```bash
python3 tools/display/make-scaler-testcard.py local/testcards
```

Writes `.svg`, `.png` and `.nv12` for 1280x720 and 1920x1080. The `.nv12` files
are staged on the board at `/root/scaler-testcard-{1280x720,1920x1080}.nv12`
(md5-verified across the link).

## Why it replaces the Leota clip for measurement

Every scaler measurement up to 2026-09-11 was taken against
`leota-av-720p.mp4`, which fights the measurement in five separate ways:

| problem with the clip | what it cost |
| --- | --- |
| the subject **moves** | apparent change had to be separated from content drift |
| mostly **dark** | magnifying into a quiet passage gives flat grey, reads as "nothing" — this is what made ramp steps 3 and 4 unreadable |
| **no scale reference** | the factor had to be estimated from the width of a face and of an eye slit |
| **no edges of its own** | clipping stayed invisible until someone thought to look for a straight boundary at full resolution |
| **77 s**, and mpv free-runs at ~2.5x | ~31 s usable window, and a silent drop to software decode at the loop point |

A static card removes all five. And `decd-client show FRAME.nv12 <dwell-ms>`
holds it with **no decoder in the loop at all** — no VAAPI, no loop point, no
free-running playback, no time limit.

## How to use it

```bash
# static, no decoder, holds for as long as you ask (ms)
ssh root@192.168.4.1 '/root/decd-client show /root/scaler-testcard-1280x720.nv12 600000'
```

Photograph or film the panel, then compare against the matching `.png` at the
same scale.

## Reading each element

**border, all four edges** — the clipping gauge. A missing edge means the output
is clipped on that side. All four present means nothing is being cut. This is
the element that would have caught the 09-11 clipping immediately.

**corner markers, each different** — TL solid square, TR three vertical bars,
BL two horizontal bars, BR a wedge. Orientation, mirroring and offset are
unmistakable; any flip or wrap shows up at a glance.

**top and left tick rulers** — 8 ticks per band, and the bands are the card's
tenths and fifths, so the reading rule is identical at every resolution: **10
bands across, 5 down, 8 ticks per band**. Count ticks per unit of screen
distance against the baseline to get the horizontal and vertical factors
independently.

**column digits 0–9, row digits 0–4** — which source region survives. A clipped
fragment now says *where it came from*, which is precisely what a piece of a
cheek could not.

**circle row with crosshairs** — the aspect gauge, and the most useful single
element. Anisotropic scaling turns a circle into an ellipse and **the axis ratio
is the H:V factor directly** — no baseline comparison, no content drift to argue
about. Five across the width also expose non-uniform scaling along a line.

**frequency blocks, periods 24/16/12/8/6/4/3/2 px** — the one element
deliberately specified in **absolute pixels**, because the filter response is
what is being probed. A real polyphase filter takes the fine blocks smoothly to
grey; a point sampler produces moiré. The tick marks under each block count its
index (1 mark = block 0 = period 24) so a surviving block can be named. Note
these are *relatively* finer on the 1080p card, by design.

**luma staircase, 16 steps** — confirms the luma path and gain are not being
disturbed, so a brightness change cannot be mistaken for a geometry change.

**resolution stamp** — the card states its own size, so a photograph of the
panel identifies which card was loaded.

Monochrome on purpose: NV12 chroma is half-resolution, and a colour pattern
would add its own artefacts to a measurement about geometry. UV is written
neutral (`0x80`). A colour variant can follow if the chroma path needs checking.

## What it should show under the current model

From [proc-scaler-ratio-ramp-2026-09-11](proc-scaler-ratio-ramp-2026-09-11/RESULT.md),
the block magnifies horizontally by `1/ratio_h` and then clips to a hard
rectangle. So with the card loaded:

- **`ratio_h` below unity** → circles become ellipses **wider than tall**, tick
  spacing increases, the right-hand columns and the right border fall outside
  the clip window, and the surviving column digits name how much was lost.
- **`ratio_h` above unity** (the untested case, and the one that matters) →
  circles become ellipses **taller than wide**, tick spacing decreases, and
  **all four border edges stay present**, because a compressed image cannot
  overflow the clip window. That is the unambiguous positive to look for.

The 1080p card exists for the actual target: feed 1920x1080 and ask the block
for 1280x720.
