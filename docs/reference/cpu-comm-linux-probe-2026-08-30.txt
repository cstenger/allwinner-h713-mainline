CPU_COMM probes under Linux -- 2026-08-30
=========================================

First time the ported driver has run on hardware. Board on Debian, normal
boot (U-Boot `h713_disp auto 0x34 logo`), MIPS parked, display live.

HOW IT WAS LOADED, and why not by reflashing
--------------------------------------------

The running kernel dates from Aug 25 and its DTB still carries
cpu-comm@3003000 with status = "disabled", so Linux creates no platform
device and the driver has nothing to bind to. Rebooting a freshly built
FIT would also have pulled in every other in-series change since that
kernel was built, which is a much larger blast radius than "does it
probe". So the module was loaded against the running kernel (vermagic
`6.18.38 SMP mod_unload aarch64` matches; MODVERSIONS is off) and a
throwaway shim repointed the node's `status` property in the live tree
and called of_platform_device_create().

  Gotcha worth keeping: for the initial device tree, property VALUES
  point into the FDT blob, which is mapped read-only. A first attempt
  memcpy'd "okay" over prop->value and took

    Unable to handle kernel write to read-only memory
    at virtual address ffffffffff60359c        <- the FDT fixmap

  The `struct property` itself comes from memblock and IS writable, so
  the fix is to repoint prop->value at a kmalloc'd buffer rather than
  writing through it. The board shrugged the oops off -- display never
  flickered -- but the module was left unremovable (stuck refcount),
  so the retry had to be built under a different name.

THE ENCODING, CHECKED AGAINST AN INDEPENDENT SOURCE
---------------------------------------------------

The shared half of the cc_ref model stores ARM-physical addresses. These
words were read back out of shared memory after the probe and compared
with values U-Boot had previously recorded from the firmware's own view
of the same ring -- so this is not a self-consistency check.

  share_seq(1,0,0) = 0x4E300000 + 0x26B8 = 0x4E3026B8
      (U-Boot's H713_COMM_CALL_SEQ_OFF is 0x000026b8)

WHAT THIS DOES NOT SHOW
-----------------------

No message has been exchanged. The MIPS is parked, so MIPS Ready stays 0
and no CALL was attempted: the corrected doorbell, the TX_IRQ_EN pulse
and the tagged-LOCAL half of the encoding are all still unexercised end
to end.

A PRE-EXISTING DEFECT THIS TURNED UP
------------------------------------

The probe logs "wrote ShMemAddr=0x4e300000 to MIPS share regs", but
afterwards

  0x03061024 : 0x00000000
  0x03061028 : 0x00000000

The write does not stick with the MIPS in reset, so the coprocessor
would never learn the shared-memory base by that route. This is old
code, untouched by the port, and it is a blocker for bringing the MIPS
up under Linux.

AFTER A REBOOT
--------------

Everything the test left behind is cleared: no modules, no /dev nodes,
node status back to "disabled", zero oops/BUG lines, taint back to the
usual 5120 (OOT + CRAP, from aic8800 and cedrus). Display and WiFi came
back normally.

The shared region is restored by U-Boot on every boot:

  magic1 @0x4E300090   : 0xDEADBEEF
  ARM flag @0x4E304CDC : 0x00000005
  MIPS flag @0x4E304CE0 : 0x00000005

-- exactly the PRE-WIPE values above, so the driver's wipe leaves nothing
behind across a reboot. Note the MIPS flag reads 0x5 while 0x0306101c is
0: U-Boot writes both flags, so that flag is NOT a MIPS-liveness signal.
