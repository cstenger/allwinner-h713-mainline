# VP9 and AV1 on H713 — a second decoder, and it is Hantro G2 family

**Result: VP9 and AV1 are not cedrus capabilities and never will be. They live
in a separate block at `0x1c0d000`, and the evidence says that block is
VeriSilicon Hantro G2-family IP — the same family mainline's `hantro` driver
already targets, including an existing Allwinner variant.**

That makes VP9 a **port** rather than a from-scratch reverse-engineering job.
AV1 is a different and much larger question; see below.

**The block was powered and read on 2026-09-23, and it responds.** See "First
contact" below: `0x0003B16D` at `+0x00` and `0x00000022` at `+0x04`, stable,
and distinct from cedrus's registers. Its real dependency turned out to be the
**VE** power domain, not the AV1 one. The session also wedged the SoC once, from
a command-ordering mistake that is written up rather than glossed.

## Why cedrus is the wrong place to look

The VE at `0x1c0e000` advertises exactly four coded formats, confirmed on the
board: `MG2S` (MPEG-2), `S264` (H.264), `S265` (HEVC), `VP8F` (VP8). That is
the whole capability set inherited from `sun50i_h6_cedrus_variant`. VP8 works
because it is *in* that engine; VP9 and AV1 are not, and no amount of driver
work on cedrus will produce them.

## The second block, already described in our own tree

| | |
| --- | --- |
| node | `av1-decoder@1c0d000` (patch 0024) |
| compatible | `allwinner,sunxi-google-ve`, `allwinner,sun50i-h713-av1-decoder` |
| reg | `0x01c0d000` (0x1000), `0x03000000` (0x10) |
| interrupt | `GIC_SPI 107` |
| IOMMU | master 5, translated (`docs/iommu-port.md`) |
| CCU | `bus_av1`, `mbus_av1` gates exist (patch 0001) |
| driver | **none binds it — inert** |

So the board plumbing is largely in place and has been for some time. What is
missing is a driver and a safe power-up sequence — the clocks all exist; see
"Gap 1: CLOSED" below, which also corrects a wrong bit in our own CCU table.

## The evidence that it is Hantro G2 family

From the vendor userspace in `local/h713-lab/ve-extract/libs/`. Reproduce with:

```sh
cd local/h713-lab/ve-extract/libs
nm -D --defined-only libawvp9Hw.so | awk '$2 ~ /^[DBR]$/ {print $3}' | sed 's/^dec_//' | sort -u
grep -oE "^#define g2_[a-z0-9_]+" <kernel>/drivers/media/platform/verisilicon/hantro_g2_regs.h | sed 's/#define g2_//' | sort
```

**1. The endianness-swap register family matches.** This is a tightly
IP-specific group, not generic terminology:

| field | `libawvp9Hw.so` | mainline `hantro_g2_regs.h` |
| --- | --- | --- |
| `pic_swap` | yes | yes |
| `dirmv_swap` | yes | yes |
| `rscan_swap` | yes | yes |
| `tab0_swap` … `tab3_swap` | yes | yes (as `tabN_swap_old`) |
| `stream_swap` | yes | yes, spelled `strm_swap` |

**2. The DWL layer.** 20 `DWL*` symbols — `DWLInit`, `DWLEnableHw`,
`DWLDisableHw`, `DWLMallocDispFrm`, `DWLFreeRefFrm`. DWL is VeriSilicon's
*Decoder Wrapper Layer*, their standard hardware abstraction. Its presence is
not a coincidence of naming.

**3. A preserved typo.** The vendor exports `dec_apf_treshold`; mainline
defines `g2_apf_threshold`. VeriSilicon's own misspelling, carried into the
vendor BSP and corrected upstream — two descendants of one source.

**4. Standard Hantro DWL config knobs**, all present as 4-byte globals:
`axi_id_rd`, `axi_id_wr`, `axi_id_rd_unique_enable`, `burst_length`,
`bus_width`, `clock_gating`, `clock_gating_runtime`, `timeout_cycles`, plus
`pVp9RegisterBaseAddr` and `dwl_shadow_regs`.

**5. VP9 and AV1 are the same block, and it is not the VE.** `libawav1.so` and
`libawvp9Hw.so` both export the `Asic*` register API (48 and 20 symbols) and the
`DWL*` layer. Every cedrus-family codec — `libawh264.so`, `libawh265.so`,
`libawvp8.so`, `libawmpeg2.so`, `libawmpeg4normal.so` — exports **zero of
either**. The split is total: two distinct hardware abstractions in one BSP,
which is what two distinct decoder blocks look like from userspace. And
`libawav1.so` contains 151 VP9 strings and shares `vp9hwd_intra_mode_tree`,
`vp9hwd_mv_class0_tree`, `Vp9DecRelease` with the VP9 library — the AV1 binary
carries the VP9 *hardware decoder* tables. One IP, both codecs.

### What this evidence does NOT establish

**It is lineage, not a register-offset match.** The comparison is between the
vendor library's exported *config globals* and mainline's *register field
names*. The vendor's actual HWIF field table (offset/shift/mask per field) is
static and not exported, and the binary is stripped — no `HWIF` strings, no
source filenames, no `hantro`/`VeriSilicon` strings survive. So this shows the
two drivers descend from the same IP documentation. It does **not** show the
H713 block is bit-identical to the H6's G2, and that difference is exactly
where a port would go wrong.

Vendor BSP libraries are also shipped across SoC families, so their presence
alone would be weak evidence. What makes it board-level rather than
BSP-level is the DT node: dedicated clocks, its own reset, its own IRQ, and an
IOMMU master port allocated to it.

## Measured on hardware, 2026-09-23 (CCU only — the block was not touched)

Reading the CCU is safe and endorsed: it is always clocked. These are
`busybox devmem` reads at base `0x02001000`, sampled while a VP8 decode ran in
a loop, so the active state is real rather than inferred.

| register | idle | during decode | what it is |
| --- | --- | --- | --- |
| `0x02001690` | `0x00000000` | `0x80000000` | `ve-core` module clock: enabled, divider 0, straight off `pll-ve` |
| `0x02001694` | `0x00000000` | `0x00000000` | never touched by the VE path |
| `0x02001698` | `0x00000000` | `0x00000000` | never touched by the VE path |
| `0x0200169c` | `0x00000000` | `0x00050005` | gates `[2:0]` = VE/AV1/VE3, resets `[18:16]` |

`0x00050005` is `0b101` in both fields: **BUS_VE (bit 0) and BUS_VE3 (bit 2)
on and out of reset, AV1 (bit 1) off.** This confirms the documented value and
identifies *which* two bits it is, which the earlier note did not.

### The finding that matters for the port: cedrus needs VE3

Our cedrus node does not ask for the VE clocks alone:

```
clocks = <&ccu CLK_BUS_VE>, <&ccu CLK_VE_CORE>, <&ccu CLK_MBUS_VE3>, <&ccu CLK_BUS_VE3>;
clock-names = "ahb", "mod", "ram", "bus_ve3";
resets = <&ccu RST_BUS_VE>, <&ccu RST_BUS_VE3>;
```

It holds **BUS_VE3 and RST_BUS_VE3** as well, and the measured `0x00050005`
is that requirement showing up in silicon.

This upgrades one item on the falsification list from a worry to a pattern.
Mainline's `sunxi_vpu_variant` asks for exactly two clocks, `{"mod", "bus"}`,
because that is what the H6's G2 needs. On H713 the *neighbouring* decoder
already demonstrably needs a sibling block's clock and reset held on. A G2
bring-up here that binds only `mod` and `bus` may come up half-powered, and
"the H6 variant does not fit unmodified" should be the leading hypothesis if it
misbehaves — not a surprise discovered late.

## Gap 1: CLOSED from the vendor kernel — there is no AV1 module clock

The answer came from the retail OTA image, not the hardware. `update.img`
carries `vmlinux.fex`: a 220 MB ARM32 vendor kernel, 5.4.99, **with full DWARF**.

```sh
dd if=update.img of=vmlinux.fex bs=1 skip=2877440 count=105860275 \
   iflag=skip_bytes,count_bytes
bunzip2 -c vmlinux.fex | tar x                      # -> vmlinux
gdb -batch -ex "p bus_av1_clk" -ex "p sun50iw12_hw_clks.hws[32]" vmlinux
```

The vendor CCU defines **no AV1 module clock**. Searching every symbol
containing `av1` yields exactly two, both gates: `bus_av1_clk` and
`mbus_av1_clk`. The only module clock in the family is `ve_core_clk`.

Resolving the vendor DT's own indices settles what `"av1"` meant:

| vendor DT index | resolves to | register |
| --- | --- | --- |
| 32 — named `"av1"` | **`ve_core_clk`** | `0x690` |
| 33 — named `"bus_ve"` | `bus_ve_clk` | `0x69c` BIT(0) |
| 34 — named `"bus_av1"` | `bus_av1_clk` | `0x69c` BIT(1) |
| 53 — named `"mbus_av1"` | `mbus_av1_clk` | `0x804` BIT(3) |

So `"av1"` in the vendor's node is a *local name for the VE core clock*. The
decoder block shares cedrus's module clock; it has only its own gates and
reset. `0x694` and `0x698` are not the AV1 module clock, because no such clock
exists — the hypothesis was wrong, and the candidate-register probe that was
step 3 of the bring-up is **no longer needed**.

### The authoritative clock and reset set

From the vendor kernel, for `av1-codec@1c0d000`:

| line | source | register |
| --- | --- | --- |
| module clock | `CLK_VE_CORE` | `0x690` |
| bus gate | `CLK_BUS_VE` | `0x69c` BIT(0) |
| bus gate | `CLK_BUS_AV1` | `0x69c` BIT(1) |
| MBUS gate | `CLK_MBUS_AV1` | `0x804` BIT(3) |
| reset | `RST_BUS_VE` | `0x69c` BIT(16) |
| reset | `RST_BUS_AV1` | `0x69c` BIT(17) |

Note it takes `BUS_VE` *and* `RST_BUS_VE` as well as its own — the same
sibling-clock pattern cedrus shows, now confirmed from the other direction.

### A latent bug this found in our CCU driver

Our `mbus-av1` gate was on the **wrong bit**. Vendor `mbus_av1_clk.enable = 8`
= BIT(3); patch 0001 had BIT(4). Every other gate in `0x804` matches
(`dma` 0, `ve3` 1, `ce` 2, `nand` 5), so this is a single transposition, now
fixed.

It is inert today — nothing requests `CLK_MBUS_AV1` — but it would have bitten
precisely at bring-up: the block would have been clocked and out of reset with
its MBUS gate still shut, i.e. alive but unable to reach memory. That is a
symptom that looks like a broken port rather than a wrong bit.

### Our DT node does not match the vendor's and should not be trusted

`av1-decoder@1c0d000` in patch 0024 currently reads:

```
clocks      = <&ccu CLK_BUS_VE>, <&ccu CLK_BUS_VE3>, <&ccu CLK_BUS_AV1>, <&ccu CLK_MBUS_VE3>;
clock-names = "bus_ve", "bus_ve3", "av1", "mbus_ve3";
resets      = <&ccu RST_BUS_VE>, <&ccu RST_BUS_VE3>;
```

Against the table above that is wrong in three ways: it substitutes **VE3** for
**AV1** in the MBUS gate and the second reset, and it maps the name `"av1"` to
a *bus gate* where the vendor maps it to the *core clock* — so as written the
node supplies **no module clock at all**.

Harmless while nothing binds it, and left unfixed on purpose: when `hantro`
does bind, the node has to be rewritten to that driver's `{"mod", "bus"}`
naming anyway, so correcting it to the vendor's naming first would be work
thrown away. Rewrite it at bind time, from the table above.

### Why the hardware could not have answered this

Worth recording, because the CCU sweep looked like the obvious route and was a
dead end. `0x694` and `0x698` sit in the VE family's window, read as real
registers, and are never touched by the VE path — so they looked like strong
candidates. But **nothing on this system ever enables an AV1 clock**, so they
read zero in every reachable state, and no amount of passive observation can
separate "module clock, currently off" from "reserved" from "does not exist".

The register sweep could only ever have produced a plausible guess. The vendor
kernel produced the fact, and the fact is that the register being hunted for
does not exist.

## VP9: two gaps left, both bounded

Mainline already has the driver *and* an Allwinner variant:

```c
/* drivers/media/platform/verisilicon/hantro_drv.c */
{ .compatible = "allwinner,sun50i-h6-vpu-g2", .data = &sunxi_vpu_variant },

/* sunxi_vpu_hw.c */
static const char * const sunxi_clk_names[] = { "mod", "bus" };
.codec = HANTRO_VP9_DECODER,
```

It decodes `V4L2_PIX_FMT_VP9_FRAME` to NV12/P010 and their 4L4 tiled forms.

**Gap 1 — CLOSED.** There is no AV1 module clock to add: the block shares
`ve_core_clk` with cedrus. Our CCU driver already has every line it needs, once
the `mbus-av1` bit fix is in. Details and the authoritative table are above.

**Gap 2 — the DT node.** The existing `av1-decoder@1c0d000` node uses
clock-names `bus_ve`/`bus_ve3`/`av1`/`mbus_ve3`, which is not what the hantro
driver binds against. A VP9 attempt needs a node with the G2 compatible, IRQ
107, and clocks named `mod` and `bus`. That is a rewrite of the node, not an
edit.

**Gap 3 — bringing the block out of reset safely.** See below. This is the only
gap that cannot be closed at a desk.

## AV1: a different order of magnitude

Mainline's AV1 support is **Rockchip-only**: `rockchip_vpu981_hw_av1_dec.c`
(VC8000D), with `rockchip_av1_entropymode.c` and `rockchip_av1_filmgrain.c`
beside it. There is no Allwinner AV1 anywhere upstream, and the sunxi G2
variant is `HANTRO_VP9_DECODER` only.

The vendor's AV1 library uses the same `Asic*`/DWL family, so the H713 block is
plausibly VC8000D-ish — but that word is carrying the whole estimate. Adapting
a Rockchip-specific AV1 driver to an Allwinner block with no reference
implementation is not the same kind of work as the VP9 port, and should not be
scoped as if it were.

**Do VP9 first regardless.** It shares the block, so it answers the clock,
reset, IOMMU and interrupt questions for AV1 at a fraction of the cost. If VP9
will not come up, AV1 was never going to.

## First contact, 2026-09-23 — the block responds

Driven by hand with `busybox devmem`, operator watching a serial console.

### It is alive

While cedrus was decoding, with the AV1 gates and reset already set manually:

```
  t6  1c0e000=0x00000000 1c0e004=0x00000000 | av1 1c0d000=0x00000000 1c0d004=0x00000022
  t7  1c0e000=0x00130001 1c0e004=0x00000100 | av1 1c0d000=0x0003B16D 1c0d004=0x00000022
  t8  1c0e000=0x00130001 1c0e004=0x00000200 | av1 1c0d000=0x0003B16D 1c0d004=0x00000022
  t9  1c0e000=0x00130001 1c0e004=0x00000100 | av1 1c0d000=0x0003B16D 1c0d004=0x00000022
  t10 1c0e000=0x00000000 1c0e004=0x00000000 | av1 1c0d000=0x00000000 1c0d004=0x00000000
```

`0x0003B16D` at `+0x00`, `0x00000022` at `+0x04`. Stable across samples, and
**not** a mirror of cedrus — the VE reads `0x00130001` at the same instant.
`+0x04` holding a small bitfield is consistent with mainline's G2 map, where
word 1 is the interrupt/status register.

This is the first evidence that the block exists as more than a DT node.

### The dependency is the VE domain, not the AV1 domain

The block answered *only* while cedrus was active, and the reason is visible in
what survived afterwards. With cedrus idle again:

| | state | set by |
| --- | --- | --- |
| `mbus_av1` (`0x804` BIT(3)) | **on** | manual, survived |
| `bus_av1` + `rst_av1` (`0x69c` = `0x00020002`) | **on** | manual, survived |
| PPU domain 4 (AV1) | **ON**, `0x00010002` | manual, survived |
| `ve_core` (`0x690`) | off | cedrus cleared on suspend |
| `bus_ve` + `rst_ve` | off | cedrus cleared on suspend |
| PPU domain 3 (**VE**) | **OFF** | owned by cedrus |

Every AV1-specific line was on and the block still read zero. It only responded
when cedrus powered the **VE** domain. So the earlier zero read was not "the
block is dead" — it was **the wrong power domain**: domain 4 alone is not
enough.

That matches the vendor DT exactly, and explains why its node lists `bus_ve`,
`reset_ve`, and `"av1"` mapped to `ve_core_clk`. The sibling-clock pattern
cedrus shows (it holds BUS_VE3) is the same pattern from the other side.

### A vendor bit confirmed against silicon

`mbus_av1` at `0x804` BIT(3) latched cleanly. Our driver's old BIT(4) would not
have, so the DWARF-derived fix is now confirmed on hardware as well as in the
vendor kernel.

### The wedge, and whose fault it was

The SoC hard-locked once: no serial output, no ssh, power cycle required —
the documented failure mode, behaving exactly as documented.

**The cause was command ordering, and it was mine.** The one-liner ran:

```
devmem 0x0200169c 32 0x00030003   <- deasserts BOTH resets
devmem 0x02001690 32 0x80000000   <- module clock, AFTER
```

That takes the VE and AV1 out of reset with **no module clock running**, which
is the hazard this document's own bring-up order warns about in step 4:
"deassert the reset — after clocks are up, never before". Collapsing six steps
into one line inverted the one rule that mattered.

The evidence pins it: `0x00010002` printed from the domain-3 power-on, then
nothing. The next command was the reset deassert.

**The correct order does not wedge.** The earlier step-by-step run —
gates, then module clock, then resets — completed without incident, and the
block was read safely afterwards. This is a data point *for* the ordering rule,
not against the bring-up.

Recovery was clean: after a power cycle all registers returned to boot defaults,
zero watchdog timeouts, zero oopses, and the VP8 gate decoded bit-exact.

### Our DT node cannot work as written

Independently of the above: `av1-decoder@1c0d000` has **no `power-domains`
property at all**. Even with a correct hantro driver bound, nothing would power
the domain, and bring-up would fail exactly where this session's first read
failed. Add `power-domains` — pointing at the **VE** domain, or both — when the
node is rewritten.

## The hazard

**Do not read `0x01c0d000`.** `docs/video-decode.md` records why: CCU
`0x0200169c` shows AV1 **gated off with its reset asserted** (bit 1 clear, bit
17 clear) — precisely the reset-before-gate condition that wedges the
interconnect on this SoC. A read there is not a probe, it is a power cycle.

The CCU is always clocked, so `0x0200169c` is free to read and is the correct
first move before anything in the VE family. Bring-up order is clock and reset
sequencing first, register access only after.

Related standing hazards in this project: a plain read of `0x07091000` wedges
the SoC, and `0x06940000` is an unpowered capture domain. The pattern is
consistent — unclocked or unreset blocks do not fault politely here.

## Prior art to not build on

`local/sun50iw12p1-research/docs/AV1_HARDWARE_DECODER_ANALYSIS.md` presents an
ioctl table as an AV1 decoder API, labelled "MAJOR DISCOVERY". It is
`decoder_display.h` — the DECD frame-submission interface — and
`DEC_FORMAT_YUV420P_10BIT_AV1` is a pixel format the *display* path accepts,
not a codec entry point. This is already debunked in `docs/video-decode.md`;
it is repeated here because it is the first thing a search for "H713 AV1" in
that tree will surface.

## Bring-up order for the supervised session

Written out because the hazard is real and the sequence should not be
improvised at the keyboard. Everything before step 4 is reversible.

**Run these as SEPARATE commands, checking each.** The one time this was
collapsed into a single line, the ordering inverted and the SoC hard-locked.

**0. Do not start from a warm board that has just soaked.** The one unexplained
concurrency failure on record happened on a cold board; keep bring-up and that
variable apart.

**1. Baseline the CCU.** `busybox devmem 0x0200169c 32` — expect `0x00000000`
idle. This is free and confirms the starting state.

**2. Power the VE domain — domain 3, not domain 4.** `0x070011a0 = 1`, poll
`0x070011a4` for bit 16. Hardware showed domain 4 alone is not enough; the
block only answers with the VE domain up. Power domain 4 as well if you like,
but it is not what makes the difference.

**3. Gate on with resets still asserted.** Set bits 0 and 1 of `0x69c` (BUS_VE
and BUS_AV1), leave bits 16/17 clear, and set `0x804` BIT(3) read-modify-write
so `mbus_dma`/`mbus_ce` survive. Read back.

**4. Start the module clock.** `0x690 = 0x80000000` — the shared `ve_core`
clock, the same value cedrus uses. There is no separate AV1 module clock; see
"Gap 1: CLOSED".

**5. Only now deassert the resets** (`0x69c` bits 16 and 17). **NEVER before
step 4.** Doing these two in the wrong order hard-locked the SoC on
2026-09-23 — see "The wedge". Everything up to here undoes by rewriting `0x69c`
to zero.

**6. Read the block.** Expect `0x0003B16D` at `+0x00` and `0x00000022` at
`+0x04` — the values it produced on 2026-09-23. Anything else is new
information. Zero means a dependency is missing, most likely the VE domain.

**7. If it responds**, the DT node and a `hantro` bind attempt follow, with the
VE3-sibling question from above as the first thing to vary if it half-works.

Keep a serial console attached. A wedge here takes the SoC, not just the
process, so ssh will tell you nothing.

## What would falsify this

- The block at `0x1c0d000` does not respond after a correct clock/reset
  sequence, or reads back an ID that is not a G2-family `AsicReadId` value.
- Mainline's G2 register offsets produce nonsense when written — meaning the
  H713 block shares the IP lineage but not the H6's register map, which the
  evidence above cannot rule out.
- The `sunxi_vpu_variant` clock/reset model does not fit (for instance if the
  block needs the VE's clocks held as well, which our DT node's `bus_ve`
  entry hints at and the H6 binding does not have).

That last one is worth flagging: our node lists `bus_ve` *and* `bus_ve3`
alongside the AV1 clocks, and the vendor's lists `bus_ve` too. If the G2 core
genuinely requires the neighbouring VE clock gated on, that is a difference
from the H6 binding and the first thing a failing bring-up should suspect.
