## The headline: hardware samples the submitted video content

A red-green-red control, three accepted submissions with identical metadata and
identical DMA addresses, changing only the constant NV12 bytes in the buffer.
Composition-page word `0x05000a60` followed the content in exact A-B-A order:

| frame | `0x05000a60` |
| --- | --- |
| red (`Y=0x51`, `CbCr=0x5a 0xf0`) | `0x0a3c0a3c` |
| green (`Y=0x91`, `CbCr=0x36 0x22`) | `0x06080608` |
| red | `0x0a3c0a3c` |

Green and final-red were each stable across five one-second samples, so these
are settled values, not transients. The panel showed the boot logo throughout,
with no flash or corruption at any point.

**What this closes:** the broad "configured but never fetched" hypothesis. Only
the frame-buffer bytes changed between runs, so something downstream of DECD's
address programming is genuinely reading the pixels.

**What it does not establish:** the word's semantics or its tap position. It
must not be called a CRC, checksum, histogram or final-output monitor yet — that
would be inferring a mechanism from a correlation, which is the specific error
this investigation has had to retract twice. All that is proven is content
dependence.

**What it leaves:** a much narrower gate. Video is fetched and sampled, and the
logo is simultaneously unchanged, so the fault is *after* the content-monitor
tap — blend participation, routing past that tap, or final output selection.

## The configured-versus-serviced question is closed

Three firmware boundaries were hooked in an authenticated `display.bin`
(SHA-256 `4380f1b3…`): PanelWinNode's dirty-mask bit-`0x800` branch into frame
programmer `0x8b1a4538`, the source-0 commit store at MIPS `0xba600014`, and
the AFBD dirty store at `0xba60006c`. Markers land in CPU_COMM shared memory,
readable from Linux at `0x4e340040`.

One bounded fmt-0 submit drove the marker from `0` to `0x6103` with dirty mask
`0xffffffff`, node mode `2`, and immediate commit/dirty readbacks both `1`.
Afterwards `0x05600014` read `0` — hardware consumed the commit — while DECD
stayed enabled with valid Y/C and advancing interrupts.

So the Linux submission reaches the firmware worker, passes the node's dirty-bit
gate, runs the real programmer, and produces a hardware-consumed commit. **Black
output cannot be attributed to an unserviced channel.**

One ordering detail is still unexplained and is a narrow future trace target:
the programmer commits control `0x03000010`, but the delayed read is
`0x03000013`, so something outside the instrumented programmer sets enable
bits 1:0. Earlier hardware already showed that setting and committing enables

## CPU_COMM works from Linux, and the suppression lead is finally closed

The 08-30 handoff ended with the transport built but no message ever exchanged.
`/dev/cpu_comm` now completes full round trips — CALL → CALL_ACK → RETURN →
RETURN_ACK — reproducibly in ~17–30 ms with zero WARN/BUG, and the driver
discovers the firmware channel itself at probe.

### The argument ABI was wrong, and the U-Boot experiment could not have caught it

The 08-30 U-Boot calls passed a leading `0` then addresses. That made each
adapter's **first** output pointer null, so the address believed to be `p1` was
actually receiving the second output. Linux wire capture settled the indexing:
the adapter is handed the message at `+0x28` (where the component id lives), so
its loads at `+4`/`+8`/`+12` are the first three payload values at `+0x2c`.
**There is no dummy parameter.**

| routine | real signature | returns |
| --- | --- | --- |
| `GetSource` | no arguments | source `0` |
| `Wce_GetActiveWindow` | **two** ARM physical out-addresses | 1920x1080, then active 1280x720 |
| `Wce_GetWindow` | **three** ARM physical out-addresses | two 1920x1080 structs, scalar `2` |

The 1/16-pixel encoding recovered on 08-30 survives unchanged; only the
indexing was wrong. Note the method failure worth carrying forward: a call that
returns successfully with a plausible-looking value is not evidence that the
arguments were interpreted the way you assumed.

That capture also found a driver bug — the channel-addressing path zeroed
message `+0x34`, which is parameter 3, and `CPUComm_CallEx` treated the same
payload word as a tgid before copying arguments over it. Tested fixed module is
SHA-256 `60bbddeab6c985607b7feb7e3d2f15d4e98704016ce8773e10a2b52bdb689608`.

## Operational hazards

Most of these cost time or a result in this session.

- **MIPS + DECD hard-locks, and no ordering cures it.** One lock happened with
  CPU_COMM loaded *before* the submit; the retry survived by submitting first
  and loading CPU_COMM after interrupts were advancing; a later run using that
  same order locked under 500 ms after `FRAME_SUBMIT` returned, before the
  delayed load began. The order reduces one overlap. **Do not keep retrying the
  live-dwell recipe** — design the experiment so the observation survives a lock
  (that is what `frame-stage-watch` is for).
- **After a module Oops, never `reboot`.** `rmmod` sticks in `flush_work` at
  refcount `-1`, and `reboot`/`reboot bootloader` from there hangs with no
  console and no ssh. Use `sync`, then `echo b > /proc/sysrq-trigger`.
- **`sysrq-b` does not sync.** An `scp`'d module still in page cache is lost and
  the board comes back on the *previous* build, which looks exactly like a code
  bug. `sync` first and check the on-board SHA.
- **Shared memory is mapped uncached.** `memcpy` on it takes an alignment fault
  (FSC `0x21`) on arm64 Device memory. Aligned `u32`/`u16` are fine; byte arrays
  need `memcpy_fromio`. Cost one Oops.
- **~90 inherited `BUG()` calls remain** in the cpu_comm sources. Six have been
  fixed and *every one was reached the moment real traffic first touched its
  path*. The `Set*`, notify and callback-registration paths are next and are
  unexercised, not known-good. Read a path's `BUG()`s before running it.
- Standing from earlier sessions and still true: `0x0152f134`
  (`EnableScreenCover`) wedges CPU_COMM and needs a physical power cycle;
  `h713_disp init <id>` means what it says about power-cycling before another
  init.

## Where to go next

**1. Capture the firmware-addressed blocks on stock Android during playback, and
diff them.** This is the highest-value experiment available and it did not exist
before this session. The 08-28 stock block sweep and the 08-29 Linux sweep
covered eleven windows — TVTOP, MIXER, DE_OSD, LAYER, AFBD, ROUTE, LVDS_PHY,
PLL, GE2D, MIPS, IOMMU — and **none of them is `0x05000000`**. The page that
carries the content-following words, and the two first-frame words nobody can
explain, has never been read on a working system.

**Widened after a static survey of the firmware**, in
[`reference/firmware-display-block-survey-2026-08-31.md`](reference/firmware-display-block-survey-2026-08-31.md).
Counting `lui` sites into the display aperture makes `0x05000000` the
*most-addressed* display block in `display.bin` — 45 sites, ahead of AFBD's 29 —
and turns up **three blocks with no mention anywhere in `docs/`**: `0x050c0000`
(22 sites, more than the display route), `0x05040000` (7) and `0x05180000` (1).
All are firmware-driven and none has ever been captured on either stack.

The same survey closes the mixer structurally. `0x0525c000` would need
`lui 0xba25` or `lui 0xba26`, and **neither immediate appears in the image at
all** — so the firmware cannot reach it. That is a third independent line after
the block sweep and the forced-write test, and the first that is not
behavioural. GE2D, TVTOP, TCON and PLL are likewise unreferenced, agreeing with
the sweep that found them static.

That is exactly the shape of comparison that produced every real lead on
08-29, and the search is now localised to precisely this page's downstream half.
`/dev/hidtvreg` reads it from stock with no root. Priority targets in the diff:
`0x05000a60` (does stock's follow content the same way?), `0x05000058`,
`0x05000104`, and whatever occupies `+0x9d8..+0xae0`.

**Take four samples, not two, or the diff is uninterpretable.** This page is not
like the eleven already swept. It mixes static configuration with free-running
telemetry — `+0xa04`/`+0xa08` are known to change between reads a second apart,
and other groups moved between an immediate and a delayed sample. One capture
per stack cannot tell a counter from a state difference, and the telemetry will
outnumber the configuration. The 08-28 stock sweep avoided this with a double
idle sample; the same discipline has to be *inside* this experiment rather than
deferred to experiment 3 below, because otherwise experiment 1's output cannot
be read.

Sample twice within *each* state, on *both* stacks — that also catches registers
that free-run in only one state, which is the real behaviour of AFBD's buffer
ring (still at idle, cycling during playback). Apparatus is built and the
classifier is tested:

```
board:  page-sample.sh ./hidtvreg-read /data/local/tmp/cap-stock   # stock
        page-sample.sh ./mmio-read     /root/cap-linux             # ours
host:   page-classify.py cap-stock cap-linux
```

It defaults to all four firmware-addressed windows plus AFBD, captured in a
single state setup — which matters, because arranging the MIPS-plus-DECD state
is the part that risks the hard lock, and one window per run would multiply that
risk. **AFBD is a positive control, not a subject:** its Y/C ring is proven to
move per frame on stock, so it must come back state-driven or free-running. If
it does not, the capture did not observe the state it claims to and a null
everywhere else means nothing. This investigation has already spent weeks on
nulls that turned out to be unfalsifiable; that is what the control is for.

It reports only registers trustworthy on both stacks whose state-2 values
differ, and lists anything free-running on one stack but not the other
separately rather than dropping it — a register that free-runs on stock and is
frozen on ours is a finding, and reading liveness out of a single sample is what
the retracted "AFBD counters are frozen" claim got wrong.

Both readers already take an arbitrary address and word count, clamp to one
page, and emit a byte-identical format, so `05000000 400` captures the whole
page on either stack with no new binary. Do not substitute `devmem`: its format
differs and the line-for-line comparison is the entire point.

**2. Trace what sets `0x05600010` bits 1:0 outside the instrumented programmer.**
Narrow, cheap, and the one loose thread the frame-service trace left. Low
expected value as a fix — hand-setting those enables is already a known negative
— but it completes the picture of who writes that register.

**3. Give the `0x05000000` telemetry words semantics before citing them.**
`+0xa04`/`+0xa08` move on their own, and until that range is classified none of
it is usable as evidence. Experiment 1 now produces this as a by-product rather
than needing its own run — `page-classify.py` emits the free-running set for
each stack — so what is left here is interpreting the words it flags, not
capturing them.

**4. Only then, more CPU_COMM.** The transport is finished and the routine table
is known, but argument signatures are not — the table publishes names and ids
and nothing else. Read each adapter with `tools/mips/disasm.py` (base
`0x8b100000`, MIPS VA `0x8b1xxxxx` = ARM physical `0x4b1xxxxx`) before calling
anything that sets state. Read-only calls 1–4 in
[`cpu-comm-client-plan.md`](cpu-comm-client-plan.md) are free and safe.

Explicitly **not** worth doing: `SetSource` from Linux (closed above), further
DECD-side format/enable/mux permutations (closed 08-28 by the blue generator),
the mixer (closed 08-29), the AFBD writeback engine (closed 08-30), and
`Wce_SetWindow` (its only real callee is a stub).

## Kernel: `patches/kernel/0071-misc-decd-fix-release-fence-lifetime.patch`

Added to `series` after 0067. `frame_item_release()` now drops the frame item's
reference with `dma_fence_put(&item->fence->base)` instead of `kfree()`ing a
`dma_fence` the returned `sync_file` still references, and
`dec_fence_ops.release()` becomes the only thing that frees it.

Two adjacent defects went with it, both reachable only *because* of that change:

- **The fence context is now reference-counted.** A fence can outlive
  `dec_exit()` now that it lives until userspace closes the FD, and `ctx->lock`
  is that fence's lock (`dma_fence_init()` is handed `&ctx->lock`). A
  `sync_file` FD does not pin this module, so `rmmod` with an outstanding fence
  freed a live fence's spinlock. This module is unloaded constantly during
  bring-up, so it is not a theoretical path.
- **`dec_frame_submit()` no longer passes a NULL fence** to
  `dec_fence_fd_create()`, which dereferenced it. `frame_item_create()` leaves
  `item->fence` NULL both when the device has no fence context and when
  `dec_fence_alloc()` fails.

Verification done: applied in series order against 0013/0033/0034/0035/0067 with
no fuzz and no offset (0035 and 0067 have pre-existing offsets; 0071 does not),
producing byte-identical sources to the intended tree; then built with
`ARCH=arm64 LLVM=1` against the pinned 6.18.38 tree — five objects, module link,
zero warnings. The prebuilt tree used for that check was restored byte-identical
afterwards.

**Why this was worth doing at all**, since a fence that signalled at submit time
would have been useless: reading the queue code confirms it signals at genuine
retirement. `dec_frame_submit()`'s own `frame_item_release()` drops only the
submitter's reference; the last one goes on the display side, when the item is
displaced from the four slots and drained through `q->last_released`, the
release FIFO and `release_work`. Conservatively late, which is the property a
retirement signal needs.

## Player: `tools/video/decd-play.c`

The five-sample ring is gone. Samples are held with their fence FDs in a
submission-order queue; a non-blocking `poll()` sweep retires from the head as
fences signal, so the common case never touches the decode path. A surface is
released only after its fence signals.

The one thing worth carrying forward is **why the eight-sample experiment
starved the pool**, which the original write-up recorded as a symptom without a
mechanism. DECD retires a frame only when a *later* frame displaces it from the
slots, so a held surface cannot be released without submitting a new one. Past
some depth that is a circular wait, not simple exhaustion: every free capture
buffer is held pending a fence that needs a free capture buffer to signal. The
hold is therefore capped (`DECD_MAX_PENDING`, default 4) and must stay below the
capture-pool size, and on reaching the cap the player blocks on the oldest fence
for a bounded 2 s and then **fails loudly naming the stalled frame** rather than
degrading to surface reuse — the degradation is exactly what produced the bands.

EOS drain is bounded for the same reason: the last submissions have nothing
behind them to displace them, so their fences never signal.

New line to read first on the next run:

```
RETIRE_STATS fence-retired=N unsignalled-at-exit=N peak-held=N cap=N stalls=N
```

`stalls=0` with `fence-retired` near the frame count means retirement kept up
without blocking the decoder. A stall is not a regression — it is the honest
report the old build could not make.

# Continuation — ROOT CAUSE: the decoder's buffer is not physically contiguous

The corruption is explained, by measurement, and the explanation is not in the
frame path at all.

```
PHYS pages=338 first=0x46f7a000 contiguous=NO breaks=31 longest-run=16(64KiB)
0x05600070 = 0x46F7A000
```

`dec_dma_map()` keeps `sg_dma_address(sgt->sgl)` and discards the rest of the
scatterlist. There is no scatter-gather in this hardware path — DECD takes one
base plus a stride and derives chroma arithmetically — so a segmented import is
read for its first segment and then walks into whatever physical memory follows.
DECD's base is *correct*: it is exactly the buffer's first page. Only the first
**64 KiB**, 51 of 720 luma lines, is actually there, and chroma at `y + 0xE1000`
is 924 KiB past the start and never in the buffer at all.

## How it was narrowed, and what each step cost

Three hypotheses died in order, and only the last one needed no operator:

1. **Premature surface reuse** — fence-driven retirement implemented and proven
   (299/300 by signalled fence, zero stalls). Picture unchanged. *Cost: one
   visual run.*
2. **Timing generally** — `DECD_FREEZE=1` resubmitted one quiescent buffer 89
   times; the corruption is *steady*. Eliminates producer readiness, frame
   mixing and fetch races together. *Cost: one visual run.*
3. **Content and layout** — dumped the buffer through the same FD DECD is given,
   bracketed in `DMA_BUF_IOCTL_SYNC`: bit-exact against a host software decode.
   Kills the NV12_32L32 tiling hypothesis. *Cost: nothing.*

Then the pagemap walk gave the answer, also for free. The lesson is the one this
project keeps relearning: **the cheap byte-level measurement should have come
first.** Both visual runs were spent on hypotheses that a checksum and a pagemap
read could have ranked in minutes.

Every prior observation now has a single mechanism — bit-exact bytes (the CPU

## The root cause, and the three hypotheses that died on the way

Cedrus's buffer is **physically scattered** (338 pages, up to 31 breaks) while
`dec_dma_map()` keeps only `sg_dma_address(sgt->sgl)` and the hardware scans
linearly from that one base. DECD's base is *correct* — the buffer's first page —
but only the first run is really there, and chroma at `y + 0xE1000` lands
outside the buffer, which is why such frames scan out overwhelmingly green.

In order, each eliminated by experiment:

1. **Premature surface reuse** — fence retirement implemented and proven
   (299/300 by signalled fence, zero stalls). Picture unchanged. *One visual run.*
2. **Timing in general** — `DECD_FREEZE` held one quiescent buffer for 89

   and fetch races together. *One visual run.*
3. **Content and layout** — the buffer dumped through the same FD DECD is given

## Important allocator implementation detail found while building

A `shared-dma-pool` on the VE node is **not sufficient by itself** while Cedrus
masters 0/1 remain behind the IOMMU. Cedrus already calls
`of_reserved_mem_device_init()` and uses `vb2_dma_contig_memops`, but the IOMMU
DMA allocator takes `iommu_dma_alloc_remap()` unless the allocation has
`DMA_ATTR_FORCE_CONTIGUOUS`; that normal path deliberately gathers scattered
pages behind one VE IOVA. The bypass DECD importer later sees those physical
pages as multiple segments.

The minimal bypass-branch change, after the carveout control passes, is both:

1. add a 64 MiB reusable `shared-dma-pool` as the VE's `memory-region`; and
2. set `dst_vq->dma_attrs = DMA_ATTR_FORCE_CONTIGUOUS` for Cedrus capture
   buffers only.

With the force attribute, `iommu_dma_alloc()` takes its contiguous path,
`dma_alloc_contiguous()` uses `dev->cma_area`, and the resulting dma-buf export
has one physical run for bypass DECD while VE masters 0/1 may remain translated.
Do not force compressed-input or codec-private allocations unnecessarily.
