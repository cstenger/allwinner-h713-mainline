## 1. DONE 2026-09-02 — both items closed

### 1a. Audio: patch 0085, the HP amp as a DAPM widget — VERIFIED

All three checks pass on hardware. Full results in [audio.md](audio.md); the
short form:

1. **Volume controls work.** A recorded ladder measured −3.50 / −7.81 /
   −12.27 dB for DAC volume 59 / 55 / 51 against 63, against 4.64 dB per
   4 steps specified. Converges to spec lower down, compresses ~1 dB at the top.
2. **The amp follows playback.** `0x324` bit 15 and `gpio-2` rise together on
   playback and return low after. Note the release is delayed by ASoC's 5 s
   `pmdown_time` — a sample taken 3 s after the stream stops still shows the amp
   up, which is not a fault.
3. **Bit 15 alone is right, for a corrected reason.** The full vendor word
   measured −0.10 dB against bit 15 alone, inside the run's own 0.25 dB
   repeatability, so the extra bits give no gain. The header claim that they
   "only raised gain" was wrong and has been fixed.

Also settled: the abandoned 0086 control-list rewrite (un-inverting
`DAC Playback Volume`) is refuted by two register reads — control 63 gives DVOL
`0x00`, control 0 gives `0x3F`, so the inherited `invert = 1` is correct.

## 2. What is proven

### Video — the chain is complete and measured

```text
Cedrus decode -> dma-buf -> PRIME import -> IOMMU -> NV12 DRM plane -> panel
```

| | |
| --- | --- |
| unpaced ceiling | 59.71 fps, every flip on its own vsync, sd 0.03 ms, 0 drops |
| PTS-paced playback | 30.06 fps on a 29.97 fps clip, `3x+=0`, nothing late |
| fragmented buffers | 56 physical breaks, 32 KiB longest run, renders correctly |
| GPU | idle throughout |

The IOMMU lifecycle in the KMS driver is **not** DECD's park/flip/unpark. DECD
only imports buffers; the KMS driver allocates its own, so the moment it joins a
paging domain `drm_gem_dma` returns IOVAs and under bypass the hardware would
scan an IOVA as a physical address. There is no working bypassing phase, so it
translates from probe (patch 0080). The Linux console itself is scanned through
an IOVA — `0x05600178` reads `0xFFC00000`.

### Audio — codec up, speaker loud

`sun4i-codec` drives the H713 codec via an H713 variant (0084) that drops two
stages H616 has and H713 does not: the DAC mixer at `0x314` and the line-out
ramp at `0x31c`. Neither register exists here, so writes to them were dropped
silently and `DAC Playback Switch` could never be set.

The speaker is on the **headphone amplifier**, not LINEOUT. `0x324` boots with
`HP_AMP_EN` (bit 15) clear; setting that one bit is what makes it loud. The
vendor's wider word `0x8F8C` measured −0.10 dB against bit 15 alone, so its
extra undocumented bits are not doing the work and are not copied.

The audio PLL was stuck at its 172 MHz boot value, making every rate play 4.8 %
slow — a 440 Hz tone measured 418.97 Hz. Fixed in 0086, which needs both
`CLK_SET_RATE_PARENT` on the codec gates and a ×1024 module-clock multiple.
Re-measured after the fix: **440.01 Hz at 44.1 kHz and 440.00 Hz at 48 kHz.**

## 3. Open work, in rough priority

1. **mpv cannot use the video plane.** This build has no `drmprime` hwdec, only
   `vaapi`, and `--drm-drmprime-video-plane` is consulted only on the drmprime
   path. mpv's VA-API route goes through `vo=gpu`, which wants a render node the
   display-only driver has none of. Best fix: an ffmpeg/mpv built with the
   `v4l2request` hwaccel, which emits `AV_PIX_FMT_DRM_PRIME`. Userspace only, no
   kernel work. A GStreamer `kmssink` client is the fallback.
2. **Capture and the rest of audio.** Playback is done — correct in pitch, level
   and routing as of 2026-09-02. Only `pcmC0D0p` exists and `dmas` is tx only;
   ADC, HDMI-in audio and the `daudio` I2S blocks are untouched.
3. **Cross-session DECD fence stall.** Did not reproduce, not disproven.
4. **Series shape for DECD.** With KMS as production, the DECD driver becomes
   dead code. Decide deliberately rather than letting it drift.

## 4. Method notes that cost real time this session

- **Re-run a known-good control before diagnosing a new failure.** Four visible
  runs went into a race that did not exist; re-running a recorded success,
  watching it fail, and finding the decoded output bit-exact is what proved the
  problem was in the setup.
- **Idle registers after a failed run mean nothing ran**, not that it ran and
  restored cleanly. That misreading cost a cycle.
- **Hash what you deployed, not what you built.** A build silently did not run
  because a `cd` moved the shell; the only thing that caught it was the deployed
  FIT hashing identical to the previous one.
- **Redirect a test client's output to files.** An oops swamped the one message
  that said where it stopped.
- **Sample during the event, not after it.** A GPIO "measurement" was taken
  three seconds into a one-second clip and proved nothing.
- **Report distributions, not means**, and count drops against the *modal*
  period — 30 fps content on a 60 Hz panel correctly holds each frame for two
  refreshes, and a naive metric calls a perfect run 100 % dropped.
- **A control that verifiably moves the right register bits but has no audible
  effect means you are looking at the wrong output.** That single inference
  found the HP amp after three separate volume experiments had come back null.
- **Check what a name maps to before theorising about it.** `speaker_vol` turned
  out to be a field already at maximum; `pa-gpios` turned out to be handled by a
  driver said to ignore it. Both were one grep away.
- **Measure before optimising.** Two apparent performance ceilings were test
  fixtures, and two predicted 60 fps blockers did not bite.

Added 2026-09-02, from the audio verification:

- **A tone is a measurement instrument, not just a stimulus.** The stuck audio
  PLL was invisible to every register check and fell out of the *pitch* of a
  recording taken to measure loudness. Record frequency even when you only care
  about level.
- **Two operating points beat one.** Testing 48 kHz as well as 44.1 kHz turned
  "the clock looks wrong" into an exact divisor, because one stuck clock across
  two nominal rates over-determines the arithmetic.
- **A `clk_set_rate` returning 0 is not evidence it did anything.** With no rate
  ops and no `CLK_SET_RATE_PARENT`, the framework rounds to the current rate and
  reports success.
- **Pick measurement steps against the noise floor you will actually have.** A
  sweep using 18.5 dB steps into a room with 18 dB of headroom left two of six
  segments unmeasurable; 4 dB steps landed all six.

## 5. Standing hazards

- Do not run real Cedrus traffic with the display MIPS alive — hard-locks the
  SoC, no watchdog.
- Do not unload `sunxi_decd` or invoke DECD PM-off after a test.
- Confirm the logo or console is visible **after** loading modules and before
  arming any visible test. U-Boot prints "logo published" on a black boot too.
- Never enable the DECD video source with no frame behind it: garbage under
  bypass, AFBD-wedging fault under translation.
- `PB5` is the backlight *and* fan enable; never hold it low.
- **Do not touch `0x0709xxxx` (CPUS/ARISC domain) from Linux — a plain READ
  hard-locks the SoC.** Confirmed 2026-09-02: `mmio-rw d 7091000 8` returned no
  output, then serial went silent and the network dropped; only a power cycle
  recovers. Our kernel neither clocks nor powers that domain, and an access to
  an ungated block on this SoC hangs the bus with no abort and no watchdog.
  This matters because the peer HDMI-RX driver ioremaps exactly that window for
  HPD control (`0x07091014`), so porting it naively will wedge the board. Bring
  the domain up first, or drive HPD through the ARISC. **A read is only safe
  when the target block is known to be powered.**
- Verify FIT **and** module hashes. `CONFIG_SUNXI_DECD=m` with no
  `CONFIG_MODVERSIONS` means a stale `.ko` loads silently against a new kernel.
