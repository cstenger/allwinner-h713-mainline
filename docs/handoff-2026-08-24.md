## 1. HEVC is complete for 8-bit Main — and Main10 now plays too

`patches/libva-v4l2-request/0005` passes the scaling matrix. Six HEVC vectors
and the H.264 ladder are bit-exact through stock ffmpeg, with GStreamer
agreeing on every one.

**The gate was structurally blind to the gap.** h01–h03 all have
`scaling_list_enabled_flag = 0`, and cedrus writes its scaling SRAM only when
that SPS flag is set — so a shim passing **no** matrix at all scored bit-exact
on every vector that existed. Two new vectors close it: `h04` (implicit HEVC
defaults) and `h05` (explicit custom lists, non-flat at 4x4, DC coefficients
differing from their own matrix — the two fields `h04` cannot see). Both read
`MISMATCH (va) ve+25` before the patch and bit-exact after. `ve+25` is the
point: the engine decoded all 25 frames both times, to the wrong answer.

A third vector, `h06`, was added later for lossless coding
(`transquant_bypass_enabled_flag = 1`) and passes. **Tiles still have no
vector** — x265 cannot emit them and no tiling HEVC encoder is installed.

**No scan conversion is needed**, which is the opposite of what the bitstream
syntax suggests: both APIs specify raster order and ffmpeg's parser has
already undone the diagonal scan. `h05` is the proof rather than the headers —
lists non-flat at every size cannot pass under a wrong permutation.

**Main10 was added last** (`0006`) and decodes on the engine: `ve+10`, PSNR y
57.07 dB, and byte-for-byte identical to the GStreamer oracle. Output is 8-bit
— see §4. Scored by `hevc-10bit-test.sh`, which is deliberately **not** part of
H1: md5 is the wrong criterion when the VE truncates and swscale dithers, and
folding a tolerance into a gate whose whole value is that md5 either matches or
does not would corrupt it.

## 3. Decode is production-hardened — and two defects were found doing it

Full write-up: [`docs/decode-production-readiness.md`](decode-production-readiness.md).
Four gates now exist where the suite previously scored only bit-exactness for
good input, single client, for under a minute.

| gate | what it scores | result |
| --- | --- | --- |
| `soak-decode.sh` | hours of decoding, md5 re-asserted **every** iteration | **5238/5238**, 195,332 frames, 2 h single-client |
| `soak-decode.sh CLIENTS=3` | the same, three at once, for hours | **4317/4317 rounds, 483,433 frames, 3 h** |
| `decode-robustness-test.sh` | survival of 16 malformed streams; verdict is a good decode **afterwards** | **16/16** |
| `decode-concurrency-test.sh` | 3 clients, different vectors across a codec boundary | **18/18** |
| `decode-leak-test.sh` | one process, one long session — the leak class a per-iteration soak cannot see | **7500 frames, RSS +12 kB, FDs flat** |
| `decode-reinit-test.sh` | mid-stream resolution change | **known-failing, see §6** |
| `hevc-10bit-test.sh` | Main10: PSNR vs software **and** byte-equality with the oracle | **PASS** |
| `hevc-decode-test.sh` / `va-decode-test.sh` | bit-exactness (existing) | **12/12**, **5/5** |

The concurrent soak is the one that matters most: the deadlock fix below had
six rounds behind it when it landed, and now has three hours. Its calibration
pass (one solo decode per vector to learn its frame count) means a single
client silently falling back to software is caught by the total interrupt
count — which is exactly how it caught *me* disturbing it, at `ve+68 expected
93`, one second after I reinstalled the driver underneath it.

**Robustness under abuse, measured on a clean boot:** 12 watchdog timeouts
from stalled decodes, five clients SIGKILLed mid-decode, three killed while a
stall was pending, two of three concurrent clients killed — healthy after
every one, zero `Failed to setup decoding job`.

The soak's per-vector wall time was flat end to end at 58–61 °C, so there is
no thermal decay at the 1296 MHz ceiling, and `CmaFree` came back +56 kB.

### Defect 1: three concurrent decoders deadlocked the engine — patch 0040

One client's teardown reset the device while another context had a job in
flight; that job never completed, `TRANS_RUNNING` never cleared, and the next
`STREAMOFF` slept forever in `v4l2_m2m_cancel_job()` in `D` state past
SIGKILL. Only a reboot recovered, and while wedged the VE was dead for every
client. **This, not a decode timeout, is the wedge this project has been
describing for weeks.**

Patch 0040's own message predicted it — *"a reset is device-wide, so with a
second m2m context mid-job this would break that job"* — and it shipped anyway.
Within-boot A/B on `sunxi_cedrus.stop_reset`: `N` gives 9/9 bit-exact, `Y`
deadlocks on round 1. Three deadlocks on `Y`, none on `N`.

**0040 is out of `series`**, and it costs nothing: it was written for the
memory corruption later traced to the 1416 MHz OPP, and its supporting A/B was
already retracted as underpowered. The file carries a header saying so.

### Defect 2: `cedrus_irq()` orphaned jobs — patch 0059, landed

The handler disarmed the watchdog as its first act and only then decided
whether the interrupt was its own. On the "not ours" path it returned
`IRQ_NONE` with the job still `TRANS_RUNNING` and nothing left alive to finish
it — the same deadlock, from a spurious interrupt instead of a reset. cedrus
has no `job_abort` op, so the watchdog is the only thing that can end such a
job.

0059 claims the interrupt first and disarms second. Verified with 0060 (debug,
out of series), which forces the branch:

| injected spurious interrupts | unfixed | fixed |
| --- | --- | --- |
| 1 | decode never returns, ffmpeg unkillable in `D`, **board needed a power cycle** | bit-exact in 1 s |
| 25 | — | bit-exact in 1 s |

No watchdog timeout fires on the fixed driver at all, which 0059's own message
did not predict: returning without disarming *or* acking means the real
interrupt is re-delivered on a level-triggered line and the job completes on
the next entry. A spurious interrupt costs one wasted handler call.

## 4. 10-bit: it already worked, and the shortcut does not exist

Full write-up: [`docs/hevc-10bit-findings.md`](hevc-10bit-findings.md).

**The standing claim was wrong.** "Main10 prerolls, reaches EOS in 40 ms having
produced zero frames" appears in `vaapi-scope.md`, the status table and two
handoffs. In fact cedrus already carries most of the upstream 10-bit series and
lacks only a fourcc, so negotiation falls back to an 8-bit format and the
buffer quietly grows for Allwinner's extra 2-bit plane:

```
471,040   NV12_32L32   640x480 luma + 640x512/2 chroma
115,200   2-bit plane  ALIGN(640/4,32) * 480 * 3/2
-------
586,240 bytes per frame, exactly what the driver reports
```

The consumer reads the first part as an ordinary 8-bit frame and it is
**correct**: 57.07 dB PSNR against a software decode, the residual being
truncation versus dithering. The 2-bit plane is 54.5% non-zero, so the engine
really is writing the full depth.

**The P010 shortcut is closed.** `VE_DEC_H265_10BIT_CONFIGURE` has a
`SECOND_OUT_FMT` field whose value 1 is P010, which would have made 10-bit a
format entry instead of a uAPI argument. Patch 0061 (DEBUG, out of `series`)
enlarged the capture buffer, pointed `OFFSET_ADDR_SECOND_OUT` at the spare room
and asked for it. **Four arms — P010 and 10-bit-4x4-tiled, each with and
without `SECOND_2BIT_ENABLE` — wrote zero bytes of 921,600**, on every frame,
while the primary and 2-bit planes in the same buffers were fully populated.
No IOMMU fault either, and that is the informative part: an output enabled but
misdirected would have faulted loudly. Silence means it never armed. The driver
never writes `VE_DEC_H265_LOW_ADDR`, whose `SECONDARY_CHROMA` field says a
second address pair exists, so the base addressing is not knowable from our
source.

**Defect 3, fixed:** the shim refused Main10 outright. Advertising it is
mechanical, but doing only that gives `ve+0` — every frame on the CPU — because
cedrus refuses a bit-depth *increase* once capture buffers exist, and VA-API
creates every surface up front. Patch `0006` declares the depth first, by
sending a minimal SPS on the fd outside any request. GStreamer never hit this
because it sets controls before negotiating the capture queue.

**Full 10-bit output still needs a V4L2 fourcc for the 8+2 layout** — which
does not exist, is where the upstream series stalled, and would additionally
need ffmpeg, GStreamer and mpv to learn it. On a panel that is 8-bit after GPU
conversion, playing the file is most of the value.

## 5. Claims retired, with their evidence — read before trusting older docs

1. **"A cedrus timeout wedges the VE for every client; reboot between runs."**
   **False.** Ten consecutive timeouts, then the shim decodes bit-exact; the
   GStreamer oracle decodes bit-exact immediately after one too. The rule cost
   real time and is retired in `vaapi-scope.md` and the 08-22 handoff.
2. **Patch 0057** (watchdog resets `ve` but not `ve3`; acks no interrupt) —
   real code observation, **no observable effect**: the within-boot A/B has
   both arms recovering. Out of `series` with the negative result attached.
3. **Patch 0058** (stall the VLD by over-programming `VE_DEC_H265_BITS_LEN`
   4x) — the engine decoded all 25 frames anyway, with the injection message
   in dmesg proving the knob fired. **That register is an upper bound, not a
   promise the hardware waits on.**
4. **"10-bit does not decode; nothing can negotiate a 10-bit format."**
   **False** — it decodes, correctly, and has all along. See §4.
5. **"A client that stalls or dies mid-decode takes the engine down for
   everyone."** **Withdrawn.** It does not reproduce on the shipping stack —
   see the abuse table in §3. Every observation behind it came from runs with
   an experimental driver installed. `patches/kernel/0062` hardens the code
   path anyway (a stuck VLD would fail every later job, because
   `cedrus_h265_setup()` reads the engine's bit reader while building one) and
   is **out of `series`** for fixing nothing demonstrable.
6. **"The resolution-change failure is the shim's format latch."** No: ffmpeg
   never propagates the change to the hardware path at all. See §6.
7. **Raw `CmaFree` is not a leak indicator.** It fell 42,908 → 7,156 kB across
   a 100-second soak and looked exactly like a leak, then returned to
   115,704 kB — *higher than baseline* — the moment caches were dropped. The
   harness now measures after reclaim and labels the heartbeat `cma_raw`.

## 6. Mid-stream resolution change — known-failing, and NOT ours

Full write-up: [`docs/hevc-resolution-change.md`](hevc-resolution-change.md).

New vectors `r01` (HEVC) and `r02` (H.264) change resolution twice. Software
and GStreamer decode them; our shim manages 26 frames of 75 and then
`Timeout when waiting for media request`.

**The obvious conclusion — ours, since GStreamer works — is wrong**, and it
took three attempts to see that. Tracing what the client actually asks for:

```
TRACE CreateSurfaces2 640x480 count=1 (current 0x0)
TRACE CreateContext 640x480
TRACE CreateSurfaces2 640x480 count=1 (current 640x480)   <- and again, and again
```

Every surface is requested at the **original** geometry for the whole stream,
no context is destroyed or recreated, and a trace comparing the SPS geometry
against the programmed format never fires. The same ffmpeg in software says
`Reconfiguring filter graph because video parameters changed to ... 320x240`.
So ffmpeg's hwaccel path never propagates the change; the shim is handed
320x240 slice data for an engine programmed at 640x480 and the VLD stalls. It
is never told. GStreamer succeeds because it drives V4L2 directly and
renegotiates itself — which is why that comparison proves nothing about us.

`WIP-0007` (geometry comparison instead of PR #38's process-wide format latch)
is out of `series`: the latch is a genuine latent bug, and replacing it is a
**no-op for this stream**.

**If you pick this up, iterate on `r01`, never `r02`.** One fails safely; the
other has twice put the board into the state where ssh answers and no command
completes, costing a physical power cycle.

## 7. How the eight retired claims died — all the same way

Every one came from a run that was measuring something other than what it
appeared to. This is the durable lesson of the session and the harnesses now
enforce it:

| what looked true | what was actually running |
| --- | --- |
| "a timeout wedges the VE" | true once, then never re-tested; ten timeouts recover fine |
| "the board runs the series module" | a `sunxi-cedrus.ko` predating two patches by weeks |
| "10-bit does not decode" | it decodes; the gate never had a 10-bit vector |
| "0058 stalls the VLD" | `BITS_LEN` is an upper bound; the engine ignored it |
| "the WIP driver fixes/breaks X" | `VA_DRIVERS_PATH` is not the variable — `LIBVA_DRIVERS_PATH` is; the installed driver ran every time |
| "the driver restore is verified" | md5 alone, which a **software** decode reproduces exactly |
| "the soak found a regression" | I reinstalled the driver under it, one second earlier |
| "a crashing client wedges the engine" | an experimental driver poisoned it; crashes do not |

What the harnesses do about it now: fail on `ve+0` rather than report a
number; fingerprint the driver and module at every heartbeat and say
`SOAK-DISTURBED`; ask `build.sh kernel-tree` which tree a configuration
produces instead of guessing; require three samples before calling a slope
flat; and stamp `/etc/h713-video-stack` at install so drift is one command
away.

## Traps worth carrying

1. **Reboot before scoring a gate that follows fault injection.** R1 was first
   run straight after the 25-injection experiment and a module swap and
   *failed* — IOMMU fault storm, repeated timeouts, wrong pixels. It looked
   exactly like a regression in 0059. From a clean boot the same module scores
   16/16. The measurement was disturbing what it measured.
2. **`pkill -f <pattern>` matches your own ssh command line** and kills the
   session. Use `pkill -x`, or kill by PID.
3. **`${PIPESTATUS[0]}` after a *function call*** reports the function's
   status, not its internal pipeline's — a `timeout` kill (124) reads as a
   clean exit. Set it inside the function.
4. **`git push` needs the sandbox off**, and the 1Password agent sometimes
   wants a second attempt.
5. **A comparison that cannot run must be an error, not a verdict.** The 10-bit
   gate first compared PSNR with `bc`, which is not on this rootfs, and
   `bc || echo 0` fails **closed** — so a 57 dB picture was reported as wrong.
   It uses `awk` now.
6. **The variable is `LIBVA_DRIVERS_PATH`, not `VA_DRIVERS_PATH`.** With the
   wrong one, libva silently loads the *installed* driver and every conclusion
   about the build under test is worthless. Confirm with a trace line you know
   only the new build prints.
7. **Never verify a driver by md5 alone.** A software decode reproduces the
   reference exactly, so a stuck engine passes. Check `ve+N` as well — it is
   the whole reason that column exists.
8. **`r02` costs a power cycle.** The H.264 resolution-change vector has twice
   left the board answering ssh with no command completing. Use `r01`.

## Next

1. **10-bit HEVC** — **answered and closed for practical purposes**, see §4.
   Main10 plays through stock ffmpeg today at 8-bit output. What remains is
   *full* 10-bit to the client, which needs a new V4L2 fourcc for the 8+2
   layout and consumer support that nothing has — a uAPI negotiation, not a
   coding task, and worth little on an 8-bit panel.
2. **A tiles vector** — needs an encoder that can emit them (kvazaar); x265
   cannot.
3. **`1392 MHz @ 1100 mV`** with its own soak, to recover most of the 8% lost
   to the 1416 removal. Still untested, still deliberately not added.
4. **Display path** is untouched by this session and unchanged: zero-copy
   playback exists only through the bespoke GStreamer/`gles-play` route, and
   mpv still needs `--hwdec=vaapi-copy`. This is now the largest untouched
   area of the video stack.
5. **Rootfs integration** is the one deployment step still manual:
   `build-va-driver.sh --install` must be run after a fresh flash. Folding it
   into the image build needs a cross-build against the target's libva, which
   is why it was not done here.
